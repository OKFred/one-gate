# 设备任务 DDD 垂直切片详细设计

## 1. 背景

AutoJS6 设备任务中心已经具备可信脚本下发、MQTT 结果回传、HTTP 回调、超时扫描和设备应用结果后处理能力，但领域规则、用例编排、持久化、MQTT 发布及 HTTP Schema 集中在 `async-task/service.ts` 中。外部调用方还直接引用 HTTP Service 或 Repository，导致业务规则难以独立测试，结果后处理通过动态导入与 `device-app` 耦合。

本次选择设备任务中心作为 DDD 垂直切片样板，只调整内部架构，不改变任何对外行为。

## 2. 目标与非目标

### 2.1 目标

1. 建立 Domain、Application、Infrastructure、Interfaces 四层结构和单向依赖。
2. 将任务标识、可信脚本参数、优先级、超时、状态转换及结果匹配规则集中到领域层。
3. 将下发、查询、结果接收、旧回调兼容和超时扫描组织为可注入依赖的应用用例。
4. 通过稳定的 Application Facade 为 HTTP、MQTT Listener、Worker Scheduler 和 Device App 提供入口。
5. 通过按 `scriptId` 注册的结果处理器解除任务中心对 Device App Service 的动态导入。
6. 为领域规则和应用用例补充无需真实数据库、MQTT Broker 的单元测试。
7. 将前端异步任务页的静态配置提升到模块级，并提取独立状态组件。

### 2.2 非目标

- 不修改数据库表、DDL 或 Migration。
- 不修改 HTTP 路由、请求响应 Schema、权限或 OpenAPI 类型。
- 不修改 MQTT v2 Topic、请求载荷或结果载荷。
- 不修改 `one-autojs6`。
- 不增加取消、Outbox、事件历史或新任务状态。

## 3. 分层设计

### 3.1 Domain

领域层不依赖 Hono、Drizzle、MQTT、环境变量或 HTTP Context，包含：

- 任务状态、终态和优先级常量及类型。
- `DeviceTask` 聚合，用于校验任务结果是否与当前任务匹配、是否允许进入终态。
- 可信脚本目录、脚本参数校验、默认优先级和超时计算策略。
- 任务 ID、设备 ID、回调地址、参数体积和结果体积等规则。
- 领域规则异常先由 Application 转换为应用异常，再由 HTTP 边界映射为现有 `BusinessError`。

### 3.2 Application

应用层定义 Repository、Device Reader、Publisher、Clock、ID Generator 和 Result Handler Registry 端口，并实现：

- `dispatchTrustedTask`：校验设备与任务，持久化后发布，发布失败时保持现有 FAILURE 补偿语义。
- `listDeviceTasks` / `getDeviceTask`：查询用例。
- `processIncomingDeviceTaskResult`：身份匹配、结果大小限制、领域后处理和幂等终态写入。
- `completeLegacyDeviceTask`：兼容旧设备应用回调，避免调用方直接访问 Repository。
- `timeoutExpiredDeviceTasks`：读取并裁剪宽限配置后执行超时扫描。

Application Facade 只暴露稳定的用例函数与契约类型，调用方不再引用 HTTP Service 和 Repository。

### 3.3 Infrastructure

- Drizzle Repository 实现应用端口，保留现有查询、排序、Compare-And-Set 终态写入和超时更新语义。
- MQTT Publisher 将领域发布消息适配到现有 MQTT Service。
- 默认容器注入真实时间、UUID、环境变量、设备查询和结果处理器注册表。

### 3.4 Interfaces

- 根 `model.ts` 继续集中 Drizzle Schema 和 HTTP JSON Schema，但枚举常量改为引用 Domain。
- 根 `service.ts` 只负责 Schema 组合、用户/HTTP Context 适配、设备令牌验证和用例调用。
- `interfaces/http/callback-url.ts` 负责从请求地址构建 HTTPS 回调地址。
- 根 `index.ts` 继续作为唯一 `encapsulation` 路由挂载入口。

## 4. 结果处理解耦

Application 持有按 `scriptId` 索引的结果处理器注册表。`mobile/index.ts` 在创建 Mobile App 时，将 `device.apps.list` 注册为 Device App 后处理器；重复创建 App 时以同一键覆盖，保持幂等。

MQTT Listener 与 HTTP Callback 调用同一结果接收用例。任务中心不再动态导入 `device-app/service.ts`，Device App 也不再直接访问任务 Repository。

## 5. 兼容性

以下契约保持不变：

- HTTP：`list`、`dispatch`、`get`、`callback`。
- 状态：`PENDING/RUNNING/SUCCESS/FAILURE/TIMEOUT/REJECTED/CANCELLED`。
- 协议：AutoJS6 v2 请求、结果和 Topic。
- 幂等：仅 `PENDING/RUNNING` 可首次进入终态。
- 失败补偿：MQTT 发布失败写入 `FAILURE/MQTT_PUBLISH_FAILED` 后继续抛出原异常。
- 超时：保留 `AUTOJS6_RESULT_GRACE_MS` 的 0 至 300000 毫秒裁剪。

## 6. 前端结构

异步任务页面继续使用 `SchemaCrudPage` 和现有 List API：

- 页面配置提升为模块级常量，避免每次渲染重新创建。
- 状态颜色映射提升为模块级常量。
- `TaskStatusChip` 作为独立组件，不在页面或表格渲染函数内部定义组件。
- 不新增前端状态、接口、文案或交互。

## 7. 测试策略

1. Domain 单测覆盖可信脚本参数、ID、URL、体积、优先级、超时、结果匹配和状态转换。
2. Application 使用 Fake Ports 覆盖正常下发、设备异常、发布补偿、结果幂等、后处理失败、超大结果、抢占标识和旧回调。
3. HTTP Service 契约测试确认四个 API 名称、路径和方法不变。
4. 执行服务端 TypeScript、定向 Vitest、服务端构建、admin 前端构建、ESLint、Prettier 和 `git diff --check`。

## 8. 后续演进

本样板稳定后再单独评估：手机端运行状态确认、取消 Topic、Outbox、任务事件历史和 Device Hub 独立包。本次不预埋字段或空实现。
