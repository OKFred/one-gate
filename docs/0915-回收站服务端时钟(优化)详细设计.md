# 回收站服务端时钟详细设计

## 背景与范围

在最新 dev（ad5c933e）建立 codex/recycle-bin-server-clock，继续完善公共回收站的期限边界。当前页面使用设备 Date.now() 判定恢复期限，设备调时会造成误判；部门恢复入口提前保存服务端时间，异步预查可能跨过到期点。

本轮改进公共列表、管理端时间判定及部门恢复最终校验。保留删除时刻起 30 × 24 小时的恢复窗口，不增加存储的到期字段，不扩展业务资源或数据库迁移。

## 服务端合同

POST /admin/maintenance/recycle-bin/list 响应增加必填非负整数 serverTimeUtc（UTC 毫秒）。完成适配器列表查询和全部异步权限判定后，再采样一次服务端时间。每行 canRestore 同时满足适配器原有业务判断和 expiresTimeUtc > serverTimeUtc。资源权限与单行业务资格保持各自含义；业务否决不会变成允许。

该字段表示响应组装时刻，不表示浏览器接收时刻。core 适配器接口保持业务无关；字段只属于通用 HTTP 响应，不增加部门专用页面分支。

部门恢复在完成删除版本、父级预查后重新采样服务端时间，立即再次检查期限，再传入带版本、期限与引用条件的单条更新 SQL。测试沿用显式固定时间参数，并通过模拟运行时钟覆盖异步跨期。最终判断不采用客户端时间；这不能消除服务进程与数据库实际执行之间的延迟，不宣称数据库提交时刻的绝对时间精度。

## 浏览器时间与生命周期

接受当前查询版本的响应时，保存 serverTimeUtc、performance.now() 和 Date.now() 的采样值。到期估计使用服务端时间加单调经过时间；墙钟不参与到期计算。定时器只触发显示更新，提交恢复时即时计算一次，避免沿用上一秒状态。

performance.now() 不受系统墙钟调整，但不同平台休眠行为存在差异。页面从隐藏恢复、BFCache 恢复时使旧锚点和旧确认失效并重新读取。每次检查比较墙钟与单调经过时间的差异，超过 5 秒仅触发重新同步。同步失败沿用既有列表失败和重试状态，不能回退到设备时间或保留旧操作。缺失、非整数或负值服务端时间同样失败关闭。

多个生命周期事件合并读取；变更已经在途时等待其结束再读取，不重新发送变更。旧请求不能覆盖新资源、结果或时间锚点。服务端采样到客户端接收存在传输延迟，不用 RTT/2 伪装精确校时；恢复接口仍检查最终期限。

## 验证与发布边界

后端覆盖响应 schema、期限前 1 ms／恰到期、异步查询及权限等待跨期、业务否决、HTTP 路由与恢复预查跨期。浏览器覆盖设备初始偏移、中途调时、单调时钟推进、tick 间提交、后台恢复、旧响应、无效锚点及变更在途重新同步。沿用已有并发、清理、迁移与权限测试。

记录修改前后 TypeScript 诊断，执行变更文件格式检查、相关测试、Node 与管理端构建、Worker 测试和 git diff --check。发布验收与本地代码验证分别记录；本轮无新增数据库迁移。真实环境只读检查新增时间字段、页面与版本，不创建或删除生产数据。

## 时间 API 依据

- [W3C High Resolution Time](https://www.w3.org/TR/hr-time-3/#clocks)：单调时钟与墙钟的区别。
- [MDN performance.now](https://developer.mozilla.org/en-US/docs/Web/API/Performance/now)：跨系统休眠差异。
- [Page Visibility API](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API)：可见性与后台节流。
- [Playwright Clock](https://playwright.dev/docs/clock)：控制墙钟、performance 和定时器的测试方式。
