## 实际实现与计划对比

| 范围      | 实际落地                                                                                                                                                                                       |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 公共层    | `core/db/soft-delete.ts` 提供独立字段工厂、固定 30 × 24 小时期、100 条批次和清理接口；业务适配器由应用入口显式注册。                                                                           |
| 部门模型  | `is_deleted INTEGER NOT NULL` 映射 Drizzle boolean，无新增默认值；服务端显式初始化 `0/null/null`。状态 CHECK、活跃名称部分唯一索引、清理索引及父部门索引同步 DDL。                             |
| 普通操作  | 普通列表、详情、树、名称查询、选择器、修改排除已删除部门；删除只改变删除及更新审计字段，保留 ID、内容和启用状态，不再调用 `exportDeletionRecord`。                                             |
| 引用保护  | 部门父级、用户部门、角色部门范围写入均以单条条件 SQL 校验；软删检查全部未删除子部门及所有用户/角色引用，包含禁用记录。用户显式 `null` 可解绑；物理删除要求先处理全部子部门，包括回收站子部门。 |
| 回收站    | 三个 POST 接口固定资源 `department`，双业务权限控制读取/恢复；提前彻底清除额外以当前加载身份的 `isSuperAdmin` 判定。页面支持搜索、分页、删除人、删除时间、到期时间、恢复和不可恢复确认弹窗。   |
| 恢复/清除 | 保留 ID/启用状态，恢复清空删除字段；父部门有效、活跃名称不冲突、未满 30 天才允许恢复。恢复/清除匹配 `expectedDeletedTimeUtc`，条件 SQL 防止旧请求及并发错误。                                  |
| 调度      | Worker/Node 现有每分钟入口调用固定注册资源，等待各任务完成；业务 Cron 失败不截断保留期清理。每类每轮最多 100 条，失败下一轮重试。                                                              |
| 历史归档  | 仅 `self/self` 且 `source_table IN ('department','system_department')`，以原 `create_time_utc + 30天` 清理；不回灌部门，不影响其他来源。                                                       |
| 元数据    | 新增菜单 107、读取/恢复/清除权限、OpenAPI 类型、中英文页面及后端消息。0014 同步已有库的菜单、权限、28 条后端翻译；仅内置角色 1 自动获得新增权限。                                              |

以下是实施中基于验证补充的细节：

- 列表返回服务器计算的 `canPurge`，避免前端把用户 ID、名称或可分配权限当作超级管理员身份。
- 同毫秒恢复再删除采用 `max(now, update_time_utc + 1)` 形成新删除版本，普通编辑不降低 `update_time_utc`。重复删除不更新时间、不续期。更新时间超前于服务器时拒绝删除并返回明确时钟冲突，避免异常历史值延长保留期；正常同毫秒边界最多前进 1 毫秒，期限仍为该删除时间加固定 30 天。
- 回收站搜索使用 `instr(name, keyword)` 字面包含，支持长中文关键词，`%` 不作为通配符。这样避开 [D1 LIKE/GLOB 模式 50 字节上限](https://developers.cloudflare.com/d1/platform/limits/)。
- 生成权限常量时发现源 `permissionSeeds` 缺少现有 `mobile.network_routing` 的读取/编辑动作，已补齐源，避免重新生成后破坏既有页面类型。
- 浏览器发现共享 Sidebar 的隐藏移动 Drawer 会让桌面页面错误进入 `aria-hidden`。将其打开条件限定为 `open && isSmallMobile`，桌面和移动端均补回归验收。
- 回收站业务数据直接适配部门 repository，没有另建重复数据存储。其他业务表和共用删除提示保持原有行为。

## 发布与运维说明

### 维护窗口

1. 确认目标库及已应用迁移，保留一致性备份/恢复点。暂停部门、用户部门、角色部门范围等相关写入，阻止旧服务与新结构混跑；迁移完成前不要开放新版清理任务。
2. D1 通过现有 `db:migrate:worker:remote` 应用追加的 0013/0014，再运行 `db:check:worker:remote`。两份 D1 迁移分开登记；若后一份失败，应保持维护窗口，排除错误后继续，不能把部分成功当作可开放状态。菜单 107 被其他业务占用时迁移会拒绝覆盖，需先处理占用。
3. Node 停止相关写入进程，对实际 SQLite 文件运行下面的专用命令（示例路径应替换为目标文件）。脚本只接受现存本地文件，默认同时处理结构和元数据；不要在正常发布中使用 `--schema-only`。

```powershell
pnpm --dir server db:migrate:department:node --database="D:/data/server.sqlite"
```

4. 新版启动后验证普通查询隐藏、部门删除/恢复、权限和超级管理员提前清除，观察至少一个分钟调度周期；核对菜单和中英文错误消息后恢复访问。到期清理按批推进，包含引用的记录会保留并报告积压。
5. 0013 改变了写入契约，旧版本既不会初始化新列也不会过滤软删除。回滚不能仅替换旧服务；保持封闭状态，按一致性恢复方案恢复代码/数据库，并重放下述删除请求后重新验收。

### 日常操作与监控

- 部门删除即进入 `/admin/recycle-bin`；管理员按需搜索并在期限内恢复。重名先处理活跃名称，父部门被删除时先恢复父部门。满 30 天立即失去恢复资格，即使调度尚未物理清除。
- 仅真正超级管理员可在不可恢复确认后提前清除；先解除全部用户/角色引用并清除全部子部门。状态变化应刷新页面后重新选择，不复用旧删除时间。
- `soft_delete_cleanup` 事件包含 `module`、`deletedCount`、`remainingExpired`、`oldestExpiredTimeUtc`、`durationMs`；有积压时为 warn。`soft_delete_cleanup_failed` 为 error，带固定错误类别，避免泄露驱动参数或记录内容。
- 生产日志平台应订阅失败事件及持续积压，检查时钟、数据库可用性、引用阻塞和每分钟处理容量；不通过把保留期重新计时来消除积压。其他业务 Cron 的开关不控制该清理。

### 删除权与备份恢复

30 天是本功能的误删恢复窗口，不是 GDPR 的统一保存期。适用删除权且无保留例外的请求应及时处理，可由超级管理员提前清除；通常一个月的答复期限不表示应等待一个月再删除。目的限制、保存期限和删除例外仍须结合实际数据及处理目的判断。[GDPR 第 5、12、17 条](https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng)

删除请求记录应在被恢复数据库之外保留最小必要的处理凭据。D1 Time Travel/其他备份有独立历史窗口；恢复旧备份后须先封闭访问，依据外部删除请求记录重放删除，再校验关联副本及权限后开放。仅运行到期任务不能阻止未到期数据在恢复后重新出现。[D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/)

本期没有建立全站删除请求系统，也没有迁移其他业务数据、日志、备份或第三方副本，不宣称完成全站 GDPR 合规。
