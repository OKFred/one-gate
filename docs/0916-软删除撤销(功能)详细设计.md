# 15 秒撤销删除详细设计

## 目标与边界

部门软删除成功后，通过公共成功浮窗提供 15 秒撤销。当前登录用户必须是本次删除人，并在撤销时仍具备部门删除权限；不要求回收站恢复权限，超级管理员也没有跨删除人的快速撤销例外。原 30 天回收站恢复规则、清理任务、数据库结构和旧删除接口保持兼容。

本次从最新 `origin/dev`（`2ed0ba6a`）创建 `codex/soft-delete-undo`。其他业务只获得可复用公共能力，本期不迁移其他业务删除入口。

## 后端合同

以下均为 POST，前缀 `/api/v1`：

| 路径                                      | 输入                                            | 成功输出 data                                                                                   |
| ----------------------------------------- | ----------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `/admin/system/department/deleteWithUndo` | `{ id, expectedUpdateTimeUtc: number \| null }` | `{ resourceType: "department", id, expectedDeletedTimeUtc, undoExpiresTimeUtc, serverTimeUtc }` |
| `/admin/maintenance/recycle-bin/undo`     | `{ resourceType, id, expectedDeletedTimeUtc }`  | 原 ID                                                                                           |

`expectedUpdateTimeUtc` 必填且允许 null，取自页面当前记录；旧 `/delete` 仍返回数值 ID。公共层提供 15000 毫秒窗口常量、收据及适配器可选 undo 合同，不反向引用部门实现。公共撤销入口保留认证和二次验证，只跳过固定回收站权限码，交由注册适配器检查对应业务的当前删除权限。未注册资源和不支持撤销的资源明确拒绝。

删除单条 UPDATE 同时判断活动状态、引用、预期更新版本及数据库当前时间晚于前次更新时间。用现有 UTC 毫秒 SQL 时间表达式写入真实删除时间，并通过 RETURNING 返回版本和 SQL 时刻；不能删除后重新查询版本。时间没有前进时返回冲突，不制造未来删除时间。

撤销单条 UPDATE 同时检查 ID、is_deleted、精确删除版本、deleter_id、有效父部门，以及 `0 <= DB_NOW - deleted_time_utc < 15000`。使用 SQL 执行时刻，不能以请求开始时采样的 Date.now 代替。恢复保留 ID 与启用状态，清空删除字段，推进更新时间。活动名称唯一索引提供并发重名保护。成功后执行现有权限缓存失效。

预查只用于友好报错，原子条件是最终依据。旧撤销请求不能恢复再次删除的记录；新删除接口携带更新版本，避免迟到删除请求在恢复后再次删除。旧接口保留原兼容语义。

## 交互、时间与身份

公共 Snackbar 支持可选 action、异步执行状态、更新/关闭句柄。部门删除成功显示名称、撤销按钮和剩余秒数；每次删除拥有独立浮窗与期限，不覆盖前一条。

15 秒从数据库记录时刻起算，包含网络与后续处理耗时。浏览器以服务端时间和本地单调时钟展示剩余时间，后台恢复、悬停、重渲染和重试都不能重置期限。截止只终止撤销资格，不能让进行中请求或失败信息无声消失。点击立即锁定按钮，禁止自动重试写操作。

浮窗保存发起删除时的 AuthSessionSnapshot；显示、点击、异步完成都检查身份，订阅账号变化立即清除旧操作。站内同身份切页保留，刷新浏览器不持久化。公共资源变更通知交给当前挂载页面刷新，避免引用已卸载组件。部门树引入请求序号和卸载保护，只让最新查询提交数据及 loading 状态。

## 失败分类

| 结果                              | 处理                                                                       |
| --------------------------------- | -------------------------------------------------------------------------- |
| 重名、父部门不可用                | 明确原因，不改名、不覆盖、不自动恢复父部门；原期限内可手动重试             |
| 过期                              | 关闭撤销入口；具备相应权限时可前往回收站，否则联系管理员                   |
| 非删除人、删除权限撤回            | 明确无权撤销，终止入口；401/TOTP 沿用全局身份流程                          |
| 版本变化、已恢复或已清除          | 状态已变化，关闭旧入口并允许刷新；不能把缺少已删除记录解释成已永久删除     |
| 超时、断网、5xx、提交结果无法确定 | 提示结果未知，不能宣称失败或仍在回收站；允许原期限内以相同删除版本手动重试 |
| 明确撤销成功、刷新失败            | 保留撤销成功结论，提示列表刷新失败并允许重新刷新，禁止再次撤销             |

失败与结果未知提示保留到用户关闭。权限允许时，通过既有列表/详情确认当前记录是否存在；当前可见只能证明当前可用，不能证明具体哪个请求恢复。无法确认就保持未知，不新增操作结果表或状态接口。

API 错误使用稳定业务码分类，兼容 AxiosError 和 HTTP 200 + ok:false 抛出的响应对象。请求层提供局部错误展示选项，默认仍全局提示；本功能更新原浮窗，保证同一错误仅展示一次，并保留全局登录与二次验证流程。

## 验证

- 双数据库驱动：权限与删除人组合、权限撤回、14999/15000 毫秒、预查或 SQL 排队跨期、同毫秒版本冲突、真实 SQL 时间与 RETURNING、旧接口兼容。
- 数据一致性：重名、父部门删除、旧删除/撤销版本、重复与并发请求、恢复或清除竞争、原 30 天恢复与清理回归。
- UI：双击、多个浮窗、失败重试、响应丢失、刷新失败、账号切换、站内切页、后台停留、键盘操作、列表响应乱序、HTTP 200 业务失败与 HTTP 错误。
- 工程：改动前后 TypeScript 对比，变更文件格式化，Node/Worker 测试，前端 E2E，Node/前端构建，Worker dry-run，最终 git diff --check。

本轮实现与本地自动化验证分别记录；发布、生产数据操作和线上验收不能由本地通过推断。没有 schema 变化，因此不运行 DDL 全量生成或迁移。
