# 健康页重设计详细设计

## 目标与现状

重设计现有 `/#/personal/health`，保留就诊/住院/检查/处方/疫苗记录与部位详情入口。现有页面把大面积霓虹人体图置于首屏，医疗记录下沉，前端缺本地翻译时直接暴露 key。目标是安静、可读、记录优先、适配移动和明暗主题，不伪造健康评分或临床判断。

## 设计流程

按 Product Design 技能先捕获当前页面及关键交互，再生成三个以现有 MUI/One Gate 主题为基础的结构方向，用户选定后实施。参考与公开设计只用空状态或明确合成记录，真实医疗记录不得进入公共测试、文档或生成素材。健康页选择不阻塞独立的 ICS 功能开发。

用户已选择按展示顺序的方案 1，并要求加入时间线。落地保留“左侧紧凑参考导航 + 右侧档案列表”结构：记录按就诊日期倒序、按月分组，在日期侧用时间线连接同组记录；类别、标题、就诊机构和操作仍保持列表的清晰列关系。移动端将参考导航折叠、记录堆叠，保留日期与时间线。直接沿用现有 MUI 图标与语义主题，无需生成装饰图片。

参考图中的额外部位与“按身体部位筛选”不照搬：现有模型没有部位关联，本期保留已支持的七个部位为辅助参考入口，不能假装筛选记录，也不展示无来源的静态生命体征。搜索仅提示后端实际支持的标题、医院和医生范围。主内容使用真实分页结果及总数，不添加无来源概览。

## 功能与安全

完整保留既有 API 与业务字段；新增、编辑、确认删除仍为用户明确操作。优化首屏标题、单一新增主操作、搜索/类别筛选、分页、记录详情与表单层次、空/加载/失败状态，避免固定只读 50 条并遗漏总数。没有数据时展示可开始录入的真实空状态，不显示虚构指标、总数或“健康正常”。

独立审阅发现旧更新/删除仅按 id、不限制记录归属；本轮必须修正为有效 human principal 的 owner+id 条件 SQL，列表 owner 必填且非法值拒绝，不给超级管理员旁路，也不允许 API Token 借创建人身份操作医疗记录。保留原 RBAC，并增加跨 owner、非法身份与并发最终条件合同测试；不读取或变更真实医疗记录进行验收。

人体/器官导航可作为紧凑辅助区域，保留部位详情入口，避免赛博扫描、持续闪烁、手工示意图主导首屏；采用现有图标库与语义色。未实现的诊断功能明确保持占位而不伪装为实时分析。只修改展示与必要前端请求协调，不顺带增加 PG 健康业务范围或改动健康数据表。

保持所有普通文字 React 文本渲染、本地中英文文案、dayjs日期、既有权限控制。请求按当前会话/代际处理乱序、换账号与离页，明确成功才关闭写入表单；保存结果与刷新失败分开，不重复全局错误。

## 验证

选定视觉后实施并对照截图；检查桌面/320px、明暗、键盘与焦点、空/加载/错误、搜索与类别/分页、详情/新增/编辑/删除确认，以及请求乱序和会话切换。只用合成医疗记录做自动化与生成素材；线上只读视觉验收，不替用户增加/删除真实医疗记录。执行改前/改后 personal TS、格式/lint、相关构建与图形验收，补实际落地与证据边界。
