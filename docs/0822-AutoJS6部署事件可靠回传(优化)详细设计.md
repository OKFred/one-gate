# AutoJS6 部署事件可靠回传优化详细设计

## 背景

生产 Hodor 运行于 Cloudflare Workers。普通 Worker 请求实例不适合维护长期 MQTT 订阅，因此手机虽然能收到部署命令并发布 QoS 1 部署事件，管理页仍可能长期停留在 `PENDING`。本次真机联调同时发现，发布包内的 pnpm 相对软链会被旧版手机客户端的归档安全校验拒绝，导致制品下载完成但无法进入激活阶段。

## 目标

1. 保留独立 MQTT 部署协议，供 Node 运行时和断网持久会话继续使用。
2. 为 Worker 增加带设备上报令牌的 HTTPS 部署事件入口，复用同一部署领域状态机。
3. 允许可信事件在中间 MQTT 阶段丢失时单调向前推进，但禁止终态覆盖、身份错配和状态倒退。
4. 新发布包不再包含归档软链，使仍运行旧校验器的客户端也能完成自举升级。

## 事件通道

手机仍向 `autojs6/deploy/v1/devices/{deviceId}/events` 发布 QoS 1 事件。启用 HTTP 上报时，同时向设备上报基地址下的 `/report/deployment` 发送相同载荷，并携带 `X-Device-Token`。

HTTP 边界执行以下校验：

- 请求符合部署事件 JSON Schema；
- 设备存在且启用；
- `X-Device-Token` 与设备当前令牌匹配；
- 部署编号、设备、版本、环境和环境修订与数据库目标完全一致；
- 新阶段相对当前阶段只允许单调前进，终态不可再次修改。

HTTP 和 MQTT 最终调用同一个 `processIncomingDeploymentEvent`。重复或晚到事件返回成功信封但不重复推进状态，以便手机安全重试。

## 丢帧恢复

部署阶段按以下等级单调推进：

1. `PENDING`
2. `STAGING`
3. `DRAINING` 或 `PREEMPTING`
4. `ACTIVATING`
5. `VERIFYING`
6. 终态

任一非终态可直接进入更高等级或终态。这用于 Worker HTTP 通道在新客户端启动后直接收到 `VERIFYING` 的自举场景，也用于 MQTT 中间事件丢失后的准确收敛。相同等级、倒退、终态后续事件和身份不匹配事件全部忽略。

## 制品兼容

CI 在生成清单前将生产 `node_modules` 中的软链物化为普通目录和文件，并在归档完成后断言不存在软链或硬链。手机客户端仍保留软链越界校验；其解析改为相对软链所在条目解析目标，仅允许最终目标留在发布根目录内。

这样同时满足：

- v2.1.3 等旧客户端可安装新的无软链制品；
- 新客户端可安全接受确实留在归档内部的相对软链；
- 绝对路径、路径穿越、设备文件和越界链接继续在解包前被拒绝。

## 安全与失败策略

- HTTP 部署事件不得携带制品签名 URL、环境密钥或 MQTT 凭据。
- 启用 HTTP 上报时，部署事件必须获得 HTTP 成功响应才允许继续；MQTT 仍作为并行审计和 Node 运行时通道。
- HTTP 失败时维持当前版本，不进行激活；失败事件仍尝试经 MQTT 持久会话回传。
- 本次不在普通 Worker 中维护常驻 MQTT WebSocket，也不扩大 Broker ACL。

## 验证

- 领域测试覆盖阶段跳跃、倒退、终态和身份错配。
- 设备令牌领域测试覆盖错误令牌；部署 facade 测试覆盖成功推进、重复事件、未知部署与身份错配。
- HTTP 契约测试覆盖 POST 路径、匿名设备权限、封闭 Schema 和统一响应字段。
- 移动端测试覆盖内部相对软链与越界软链。
- 发布构建验证归档无软链、摘要稳定、清单逐文件一致。
- Pixel 5 验收验证旧客户端下载无软链制品、原子切换、HTTP `VERIFYING/SUCCEEDED`、Gate 状态收敛和回滚保留。
