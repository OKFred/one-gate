# 设备注册与上报 DDD 垂直切片实际落地

## 1. 落地结果

已将 `mobile/device` 从接近千行的混合 Service 重构为 domain/application/infrastructure/interfaces 四层，并新增稳定 facade。HTTP 路由、Schema、权限、D1 表、MQTT v2 载荷、令牌、加密 AAD、在线窗口、事件幂等与定时维护行为保持不变。

根 `service.ts` 从 939 行降至 371 行，仅保留 JSON Schema、HTTP adapter、权限和 facade 调用。设备用例集中在 `application/device-center.ts`，纯规则进入 `domain`，Drizzle 与 WebCrypto 实现在 `infrastructure`，HTTP 错误和请求头读取进入 `interfaces/http`。

## 2. 实际变更

- 新增设备在线、Presence、能力、标识符、事件时间窗、摘要和掩码领域规则。
- 将 reportedExtra 与自定义元数据规则迁入 Domain。
- 新增不依赖框架、Drizzle PO 或根 Model 的 Application Ports 与 `DeviceCenter`。
- 将原 Drizzle Repository、AES-GCM/Token 实现迁入 Infrastructure，并由默认容器装配。
- 新增 `device/facade.ts`，统一提供管理员 CRUD、上报、事件、维护、任务目标查询和日志标签。
- `mqtt/listener.ts`、Worker Scheduler、async-task HTTP callback 与任务中心设备读取均迁移到 facade。
- 根 `model.ts` 继续集中 Drizzle 与 JSON Schema，设备事件和状态常量引用 Domain，避免枚举漂移。
- 删除根级 `repository.ts`、`crypto.ts`、`metadata.ts` 业务实现；Git 将其识别为迁移到分层目录。

## 3. 与计划的差异

- 计划中的 HTTP token 适配器和错误适配器均已落地，并额外在 async-task callback HTTP 边界组合设备错误适配器，保持无效设备令牌仍返回原业务错误，而不是 500。
- 元数据规则已迁入 Domain，但为了严格保持旧错误状态语义，原先由元数据工具直接抛出的结构异常不转换为 `DeviceApplicationError`；原先由 Service 主动校验的设备协议规则继续映射为现有业务校验错误。
- MQTT Listener 原先复用 `metadata.isRecord`；为了避免 Listener 依赖设备 Domain 私有工具，边界改为声明自己的最小普通对象类型守卫。
- 未保留根级兼容导出，因为仓库全量搜索确认不存在其他调用方。

## 5. 复盘记录

本轮完成两次重新复盘：

1. 恢复元数据结构错误的旧异常边界，避免纯重构改变边缘 HTTP 状态。
2. 修复 async-task callback 跨切片调用设备令牌校验时的错误映射，避免无效令牌从业务错误退化为 500。

## 6. 数据与部署影响

本次没有修改 Drizzle 表、D1 DDL 或 migration，不需要执行远程 DDL、`db:init` 或额外数据同步。合并后按现有 GitHub Actions 部署 Worker 即可。

## 7. 后续建议

下一切片建议选择 `mobile/device-app`：它仍将 HTTP、设备 App 同步、任务下发和结果后处理集中在 `service.ts`，并直接依赖 async-task 的 HTTP callback/error 工具。可复用本轮的 facade、Application Ports 与接口边界模式继续收敛。
