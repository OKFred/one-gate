# 定时任务诊断与初始化优化实际落地

日期：2026-10-23。基线：`main@9c5942cf`。分支：`codex/hodor-maintenance-diagnostics`。

## 实际变更

| 范围             | 实际行为                                                                                                                                                                                 |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 定时维护诊断     | 七类维护使用固定任务名称；一次调度共享 `runId`。失败时立即记录安全原因码、时间和耗时，所有任务结束后才汇总并拒绝该次调度。                                                               |
| 回收站清理诊断   | 保留既有 `CLEANUP_FAILED`，增加固定 `causeCode`，资源清理日志与外围调度使用相同 `runId`。                                                                                                |
| 原因分类         | 有限深度检查异常 cause 链，只读取自有数据属性；识别 D1 连接中断、D1 类别、选定 PG SQLSTATE、SQLite BUSY/CONSTRAINT 的明确扩展码。未知值为 `UNKNOWN`，不序列化原始错误、SQL、参数或凭据。 |
| scheduled 初始化 | 绑定及环境注入后调用 `ensureAdminRegistry()`，直接初始化服务注册表，跳过 `createApp()` 的 HTTP 路由构造。                                                                                |
| 注册表复用       | 依据实际注册表是否存在判断，保留显式安装的 override；显式 `initAdminRegistry()` 仍可重建。首次 fetch 与首次 scheduled 的先后顺序均可用。                                                 |
| 后端范围         | D1 Worker 仍运行原七项任务，SQLite Node 仍运行 Cron 和 retention，PG Node/Worker 仍只运行 retention；PG 注册及维护处于数据库作用域内。                                                   |

不新增即时重试；一项任务失败不会跳过其他维护工作。没有接口、权限、数据库迁移或保留期变更。

`one-autojs6` 原客户端对话完成了独立的 `mobile/src/report-error.ts` 和测试补丁：HTTP 错误及 `200 + ok:false` 保留安全业务码、固定原因和已知字段名，兼容真实 Schema 的嵌套字段路径。已知原因包含设备认证三类错误及 `INVALID_OPERATIONS_CAPABILITY`；附加任意内容的变体仍不输出。此跨仓库补丁保留在客户端工作区，本仓库未复制其源码。

## 与计划的差异

总体按先诊断、再初始化优化的顺序完成。为便于单独验证，将具名任务包装从 `soft-delete-cleanup.ts` 拆至 `scheduled-maintenance.ts`，旧模块保留重导出。

复核共两轮，第一轮发现并修正两项问题：失败日志不能等待其他任务结束才输出；SQLite 不能只识别基础约束码而遗漏驱动实际返回的扩展码。第二轮未发现剩余阻断项。依工作流先暂存已有改动，再修正并重新验证。

额外增加真实内存 libsql 约束错误测试和真实 workerd scheduled 集成测试。未扩大设备能力权限或修改生产配置。

## 初始化性能证据

本地实际应用包含 374 条路由。原入口通过应用构造初始化服务；新 scheduled 入口构造 HTTP 路由数为 0。真实 workerd 功能测试与工厂调用测试共同覆盖这一分离。

Node 15 次调用对照中，原应用构造累计 CPU 采样为 141,000 微秒；新 ensure 调用低于此次 Windows CPU 采样分辨率，显示 0。不能据此声称 CPU 为零或降低 100%。该对照排除了静态导入与数据库等待，也不等同于生产 Worker CPU。

静态模块仍会进入 bundle；业务 Cron 扫描和执行器本身未在本轮优化。线上 CPU 收益与是否消除历史超限，需要发布后用相同调用类型和数据规模验收。

## 422 与 D1 排查结论

### Presence

客户端对话定位到设备身份配置误用，恢复既有身份后返回 `200 + ok:true`。本轮独立只读观察了三个连续自然心跳，均 HTTP 200、Worker outcome 为 ok；D1 的 `last_heartbeat_time_utc` 同时持续前移。在线状态切换字段 `last_online_time_utc` 不能用作心跳新鲜度依据。

### Device Info

当前源码存在明确协议不一致：客户端 `DEVICE_OPS` 包含以下五个名称，而服务端 `mobile/device/domain/device.ts` 的 capabilities 正则会拒绝它们，抛出 `Invalid operations capability`：

- `device.screen.brightness.get`
- `device.screen.brightness.set`
- `device.ui.target-at`
- `device.telephony.get`
- `device.alert.find`

亮度操作包含额外路径段；其余类别或连字符不在当前规则内。客户端已补对应安全诊断码。这是已定位、尚未修复的接口合同冲突；本轮短窗口没有新的 Device Info 请求，未主动触发上报或宣称线上恢复。

下一步应核对服务端执行白名单、客户端实现和版本兼容，制定明确共享合同及回归用例，避免仅放宽任意字符串正则。

### D1

历史证据为旧版本 83 个失败 span / 19 个 trace 的 `Network connection lost`，不能把 span 数解释为独立事故数。官方文档将其描述为特定 D1 数据库实例的网络错误；尚不能确定具体平台事件、区域、Worker 取消或 CPU 超限的因果关系。

本轮约 170 秒自然流量观察中，三个 scheduled 均成功，CPU 为 50/36/61 ms，未见连接中断，清理积压为 0。全部属于线上原版本，是诊断观察，不能作为本轮优化效果或根治证明。公开状态历史中未找到直接匹配的事件，也不能排除单实例未公开故障。

后续使用新增任务日志关联同一 invocation/trace 的版本、CPU、outcome、D1 span 和时间；继续避免未知提交结果下重放写入。
