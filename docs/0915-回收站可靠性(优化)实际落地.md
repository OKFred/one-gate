## 实际改动与计划差异

- 公共执行器显式选择日志字段；适配器额外返回的实体快照、同名 event/module 或其他私有字段不能进入结果日志。成功空轮也输出 info，存在到期积压输出 warn。
- 新增 `checkedTimeUtc`、`cutoffTimeUtc`、`overdueMs`，耗时限制为非负数。统计要求非负安全整数、删除数量不超过 100，最早到期时间与积压状态一致；异常返回记 `CLEANUP_INVALID_RESULT`，执行异常记 `CLEANUP_FAILED`。两类失败均继续后续资源，最后让本轮失败，供下分钟重试。
- 返回统计校验只能识别适配器违反合同，不能追回已经执行的删除；实际批量上限仍由业务 SQL 保证。没有要求“删除数＋剩余数＝初始总数”，以保留并发清理和恢复语义。
- Workers 配置只增加包内 node_modules 排除规则，原有 include、别名及插件版本保持不变；相较设计中的限定源码根目录方案，这是已证实的更小改动。
- 实际增加测试插件 `remoteBindings: false`。首次测试触发无关远程 AI 绑定连接并超时，局部结果不计验收；关闭测试远程绑定后，9 个目标文件完整执行通过，未建立远程会话，也无关闭超时。生产 Wrangler 配置与绑定未修改。
- 部门 SQL 已先排除引用再限制批次，无需修改。补充 100 个更早到期且被禁用用户引用的部门与后续可清理部门混合的回归；逐轮计数、最早到期时间及解除引用后的清理均准确。
- 使用现有 `recycle-bin-resources.integration.spec.ts` 验证真实应用组合，而非增加独立调度测试文件；验证部门和历史归档各自的空轮日志及批量积压日志。
- 页面新请求开始清除旧结果和选择，失败保留查询用于重试；未就绪时不显示分页，成功分页使用服务端返回页码/总数。恢复或清除成功后刷新失败时，旧记录不再可见或可操作。变更请求失败仍保留原确认记录及删除版本。

公开 API、OpenAPI、数据库结构、菜单权限、30 天保留期、业务引用约束均无变化，资源仍仅注册部门。

## 清理日志操作说明

在 Worker 的 Observability 中按结构化字段过滤。Cloudflare 会提取对象日志字段供查询；该行为见 [Workers Logs 文档](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)。Node 由现有进程日志采集同样字段。

| 目的           | 过滤与解读                                                                                                               |
| -------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 确认资源已检查 | `event = soft_delete_cleanup`，再按 `module` 分别选择 department 或 legacy_department_archive，检查最近的 checkedTimeUtc |
| 确认空轮正常   | deletedCount=0、remainingExpired=0、oldestExpiredTimeUtc=null、overdueMs=0；该事件证明适配器本轮返回了空统计             |
| 找到到期积压   | remainingExpired>0，按 overdueMs 降序；oldestExpiredTimeUtc 是最早到期时刻，不是原删除时间                               |
| 找到失败       | `event = soft_delete_cleanup_failed`；CLEANUP_FAILED 表示执行失败，CLEANUP_INVALID_RESULT 表示适配器统计违反合同         |
| 判断重试恢复   | 对同一 module 检查后续成功事件及积压是否消退；单轮失败不跳过其他资源                                                     |

每分钟按显式注册资源逐个处理，每类最多 100 条；部门清理遇到引用仍保留记录并报告积压。检查时刻减去固定 30 天得到 cutoffTimeUtc，不存储预计算到期列。每个完成的资源检查会有一个结果或失败事件；终止、超时或日志采样可能造成缺失，不能只凭日志沉默判断正常，应同时检查 invocation 状态与采集设置。

上线时按具体 Worker 版本过滤，验证连续三个周期的两类资源事件、健康检查和版本；比对发布前后的聚合计数。当前生产回收站为空时只做只读验收，不制造删除数据。本轮没有配置外部告警订阅，也没有新增生产数据库迁移或 Node 实例部署。

## 后续与既有诊断

客户端时钟偏移导致前端恢复按钮提前失效可单独优化；服务端期限检查仍为最终依据。外部告警通知、备份恢复后的删除请求重放及其他资源迁移分别治理。

本轮没有新增待修复的 TypeScript 问题。后端根配置的 6 条既有诊断：mobile app-version/repository.ts:77、mobile app/repository.ts:66、mobile async-task/infrastructure/repository.ts:70 的 SQL 类型问题；scripts/test-mobile-device-reporting.ts:301 的模块顶层 await；scripts/test-mobile-device-security.ts:7 和 :11 的两个缺失模块引用。实际服务应用编译配置不受影响。
