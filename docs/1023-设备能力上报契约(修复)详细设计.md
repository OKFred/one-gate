# 设备能力上报契约修复详细设计

日期：2026-10-23。基线：`87fad15f`。分支：`codex/hodor-maintenance-diagnostics`。

## 问题

Mobile 当前固定上报 15 个受控操作名称。服务端设备领域使用类别和单段方法正则校验，拒绝其中的亮度 get/set、UI target-at、telephony get 和 alert find，导致整个 Device Info 返回 422。已经上线的安全诊断将这一错误识别为 `INVALID_OPERATIONS_CAPABILITY`。

原正则还接受受控清单以外、但格式相似的名称。因此本次使用精确固定集合，同时解决合法能力被拒绝和未知能力被接纳的问题。

## 方案

在设备领域定义设备可报告的操作清单，内容镜像客户端 `mobile/src/ops-protocol.ts` 中现有 `DEVICE_OPS` 的 15 项。`validateCapabilities` 逐项精确匹配该清单，不改变大小写、不 trim、不接受额外路径段或任意命令。保留 ops 协议版本 1、boolean enabled、`arbitraryShell=false`、最多 50 项等既有信封约束，并继续复制输入数组。

设备能力报告只是元数据，不是执行授权。当前 Durable Object 运维通道仅允许原有 10 项操作；本次不修改其执行白名单、会话权限、令牌、参数校验或客户端实现。五项新增可报告的能力不因上报成功而获得服务端执行许可。

清单置于设备领域内，不新增跨仓库运行时依赖，不让应用或基础设施层反向控制领域校验。测试用固定客户端协议样本对比，防止只验证实现常量自身。

## 验证和交付

- 合法 15 项整体及原冲突五项逐项通过；旧版受控子集和空列表继续通过。
- 未知类别、未知方法、shell、任意命令、大小写变体、空白和额外后缀、非字符串、非法信封及超过 50 项仍拒绝。
- HTTP 报告经现有设备认证和应用层校验后返回 `200 + ok:true`；非法能力返回稳定业务错误且不更新设备快照。
- 聚焦 Node 和 workerd 测试、TypeScript 前后对比、格式与 `git diff --check`；由发布方统一执行构建、打包和生产部署。
- 发布后由已获授权的客户端对话重启 Mobile 进程，验证一次真实 Device Info 和自然 Presence，保持日志脱敏。

本次无数据库、接口形状、可分配权限、前端或部署配置变更，无需迁移和种子同步。发布与真实设备验收分别记录。
