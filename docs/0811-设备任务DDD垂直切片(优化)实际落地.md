# 设备任务 DDD 垂直切片实际落地

## 已落地范围

- 在 `server/packages/admin/src/mobile/async-task` 内完成 AutoJS6 `async-task` 垂直切片，形成 `domain`、`application`、`infrastructure`、`interfaces/http` 四层结构。
- `domain` 集中维护 `DeviceTask` 聚合、状态与优先级、可信脚本目录、参数/超时/体积规则、四元组匹配和终态转换。
- `application` 以 `DeviceTaskCenter` 编排下发、查询、结果接收、旧回调和超时扫描，并通过 Repository、Device Reader、Publisher、Clock、ID Generator、Settings、Result Handler 端口访问外部能力。
- `infrastructure` 提供 Drizzle Repository、MQTT Publisher、环境配置和默认生产依赖装配。
- `interfaces/http` 负责回调 URL 与应用异常到 `BusinessError` 的映射；根 `service.ts` 仅保留 Schema、HTTP 参数适配和四个 API 定义。
- 根 `facade.ts` 作为 HTTP、MQTT Listener、Worker Scheduler 和 `device-app` 的稳定入口，不再依赖 HTTP 错误类型，也不向调用方暴露 Repository。
- `model.ts` 继续集中维护 Drizzle 和 JSON Schema，并引用领域层状态、优先级和可信脚本常量。
- 新增 `mobile/bootstrap.ts`，由 Mobile 路由入口和 MQTT Listener 显式、幂等注册 `device.apps.list` 结果处理器，替代结果流程对 `device-app/service.ts` 的动态导入。
- 管理端只读列表提取独立 `TaskStatusChip`，提升状态/优先级映射和页面静态配置，并继续复用生成的 OpenAPI 类型。

## 兼容性结果

- 数据库表、列、索引和迁移未修改。
- HTTP 默认 API 对象仍仅包含 `list`、`dispatch`、`get`、`callback`；路径、POST 方法、权限、请求和响应 Schema 保持不变。
- AutoJS6 协议版本仍为 2，MQTT Topic、载荷字段、QoS 和发布审计语义保持不变。
- 下发流程仍先入库再发布；发布失败仍补偿写入 `FAILURE/MQTT_PUBLISH_FAILED`。
- 结果仍校验 taskId、deviceId、scriptId、traceId，重复终态、晚到结果和不匹配结果仍不重复完成任务。
- 非法 callback URL 保持旧实现的原生 URL 异常语义；非 HTTPS 地址继续映射为业务错误。
- 旧手机客户端 callback、结果过大转换、结果后处理失败转换和超时宽限上下限保持原有行为。
- 未修改 OpenAPI 生成文件、权限、菜单、翻译种子和 `one-autojs6`。

## 与计划的差异

- 稳定应用门面实际放在 `async-task/facade.ts`，便于保留现有模块入口；其实现直接委托 Application，不包含 HTTP 错误映射。
- 新增 `mobile/bootstrap.ts`，并同时由 `mobile/index.ts` 与 MQTT Listener 调用，覆盖完整应用启动和 Listener 独立启动两条路径。
- 额外将 `mqtt/service.ts` 的发布审计参数收窄为最小 Actor 类型，解除 Application Actor 对 `UserObj` 的间接依赖；同时清理该变更文件的既有未使用导入和空 catch lint 问题。
- 超时 Repository 端口接收 Application 使用 Clock 算出的截止时间和完成时间，使 Fake Clock 能完整验证超时策略。
- 在原计划四个测试文件基础上新增 callback URL 测试文件，并将测试总数扩充到 56 个。

## 复盘结论

- 第一轮复盘发现并修正：Facade 反向依赖 HTTP、超时策略仍使用基础设施时间、应用测试依赖 Core/Drizzle 类型、Schema 证据不足、非法 callback URL 错误语义变化，以及初始化契约和非有限超时边界。
- 第二轮复盘确认上述修正没有引入新的依赖倒置、接口或协议兼容问题，未发现新的 P1/P2。
- 设备结果后处理与终态持久化之间仍沿用旧实现的跨进程竞争边界。单库条件更新保证只有一次终态写入，但多进程并发重复结果仍可能在写入竞争前重复执行后处理器；本轮为保持数据库和状态模型不变，没有引入任务领取状态、Outbox 或分布式锁。

## 后续建议

- 若部署形态出现多个并行结果消费者，下一阶段为结果处理增加数据库原子领取或可恢复的 Outbox/Inbox，而不是依赖进程内锁。
- 手机端状态确认、取消、Outbox 和事件历史继续作为独立阶段设计，不在当前协议或表结构中预埋字段。
- 将本切片的 Domain/Application/Ports/Adapters 目录和 Fake Ports 测试模式复制到下一个边界清晰、变化频繁的后端模块，避免一次性拆分整个 `node_server`。

本次修改没有新增未处理的 TypeScript 错误。
