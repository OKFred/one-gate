# 管理后台底座详细设计

## 1. 架构目标
本设计旨在满足项目在多租户环境下的微服务拆分需求，将原始单一的底座配置 `base_config` 进行三层解耦拆分，分为：
1. **系统底座配置 (System Config)**: 面向整体系统的基础设施配置（如对象存储、默认邮件服务器）。
2. **个人用户配置 (User Config)**: 面向 `personal` 模块的个体偏好配置。

## 2. 数据库设计
使用 Drizzle ORM，分别在各子包中定义对应的 Schema：
- `@hodor/admin`: `base_sys_config`
- `@hodor/personal`: `base_user_config`

两张表的主要差异在于隔离维度（Index Key）：
- `sys_config` 是全局唯一定位的，依赖 `namespace`。
- `user_config` 具有 `userId` 维度隔离。使用复合索引 `idx_base_user_config_user_namespace`。

## 3. 缓存策略 (KV Cache Layer)
底层调用 `@hodor/core/middleware/cache` 中基于 `workerd` 的 `KVStorage`。
为了避免复杂的分布式锁或者并发冲突，并结合 Cloudflare Workers 架构的特性，采用 **Cache-Aside / Eventual Consistency（最终一致性）** 策略。

### 3.1. 缓存清理机制
1. 前端触发 `add`, `update`, `delete` 等操作。
2. 接口层先执行数据库 ORM 的 DML 持久化操作（Drizzle SQLite）。
3. 数据库操作成功后，发起 `kv.delete()` 请求清理对应命名空间的缓存 Key。
4. 返回 HTTP Response。

### 3.2. 缓存重建机制
1. 前端或后端内部调用获取配置（如 `getMergedConfig`）。
2. 调用 `kv.get(cacheKey)` 检查缓存。
3. 缓存命中则直接返回，否则查库后直接组装默认值并使用该结果返回给调用方（在下一次高频请求或专门的缓存预热机制中再做写入，或在查询后立刻执行 `kv.put`，本项目中直接返回实时查询并在必要时做内存穿透缓存）。

## 4. 模块依赖与跨服务调用
通过 `admin/common/registry.ts` 构建服务注册中心。所有的模块（含 Admin）在需要提供服务时，会在应用启动时注册到总线上。例如 `rpaRegister`。
当 `biz_config` 需要提取某个 `namespace` 的 Provider（如获取默认值配置 `getDefaultValues()`）时，通过 `registry` 进行反向查找，以此实现强解耦。

## 5. API 规范
- 所有路由路径符合 Restful 前缀：
  - `/api/v1/admin/base/sys_config/*`
  - `/api/v1/enterprise/base/biz_config/*`
  - `/api/v1/personal/base/user_config/*`
- OpenAPI JSON Schema 定义集成在对应的 `service.ts` 文件中，并通过封装好的中间件拦截器强制类型校验。
