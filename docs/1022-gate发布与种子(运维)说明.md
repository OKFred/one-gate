# gate 发布与种子同步

## 结论与当前验收边界

2026-10-22 的浏览器检查中，`gate.this-time.com` 已登录超级管理员，但缺少“企业与成员”“资产台账”，直接访问两个页面均进入 NotFound。当前前端会以服务端菜单树校验路径；菜单缺失本身足以触发 404，不能据此断定前端包一定是旧版。

随后对公开静态资源的只读核对确认，当前 Admin 使用 `https://hodor.this-time.com` 作为 API，Enterprise/Personal 远端模块分别来自 `gate-enterprise.this-time.com`、`gate-personal.this-time.com`。四端公开 `version.json` 均为 `20260919193143-db2a14fc`，因此当前实际部署也尚未包含本轮资产代码。版本与路由证据用于确定发布目标，不代替数据库或功能验收。

One Gate 公开仓库的 CI 只运行测试、类型检查、构建和 Worker dry-run。合并 `main` 不会更新线上 D1、Worker 或 Pages。旧归档仓库的 `dev/master` 私有流水线不会因新仓库 `main` 合并而触发。

本说明及预检工具不代表已经发布、远端迁移或通过线上业务验收；所有验证结果应分别记录。

## 各命令实际更新哪里

以下现有命令均从 `server/` 执行，前端构建除外。

| 命令                                | 目标与作用                                                                                              |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `pnpm run db:init node`             | `DB_FILE_NAME` 指向的本地 SQLite；执行全量结构和基础种子。不会同步远端 D1。                             |
| `pnpm run db:init worker remote`    | 根据当前配置向远端 D1 执行全量建表文件，不调用基础菜单/权限种子。已有库升级使用编号迁移。               |
| `pnpm run db:migrate:worker:remote` | 向当前配置的远端 D1 应用未执行的编号迁移，并写 Wrangler 迁移账本。属于远端写操作。                      |
| `pnpm run db:check:worker:remote`   | 执行现有完整结构契约，主要验证数据库结构；不证明前端和业务验收通过。                                    |
| `pnpm run sync:permissions`         | 从后端权限常量生成前端 `usePermission.ts`，不写数据库。                                                 |
| `pnpm run sync:schemas`             | 默认只生成系统表单配置 SQL；带 `--local` 或 `--remote` 才向对应 D1 导入。不会补菜单。                   |
| `pnpm run sync:schemas --remote`    | 写 `system_schema_form`，并清理已不在当前系统注册集合中的系统表单，保留用户来源表单。不是菜单种子同步。 |
| `platform/` 下 `pnpm run build:all` | 构建 Admin、Enterprise、Personal 三个前端；之后仍须发布对应 `dist`。                                    |

`db:init node` 在本地进程更新的内存权限缓存版本，不会失效线上 Worker 的 KV。

## 非 reset 不等于无损

现有 `initDatabase({reset:false})` 会执行下列行为：

- 菜单：删除不在内置菜单 ID 集合中的记录，按 ID 更新已有菜单的名称、图标、顺序、路径、父级和业务标识。
- 权限：删除不在当前权限种子集合中的权限及孤立关联；自动给平台角色 1 补充权限。
- 翻译：覆盖相同 key/语言的值、哈希和启用状态；语言同步会更新启用及顺序。
- 管理员：现存密码不会被更新，但用户的角色数组、语言、启用状态，以及平台角色的启用、删除状态和数据范围会被覆盖。

所以，即使允许全量同步，也应先满足“不丢失已有数据”的前提；不能把去掉 `reset` 当作该前提的证明。本轮资产升级已有定向的 `0016/0017`，无需为了显示两项菜单重跑全量初始化。若未来确需全量种子维护，应另行提供保留已有记录的模式、冲突报告和差异审查；本次未改写现有种子同步行为。工具清理后的当前入口见[数据库迁移说明](database-migrations.md)，旧 `db:init node migration` 已停用。

## 资产发布只读预检

从 `server/` 运行：

```sh
# 两种目标都必须显式选择，不会默认连接生产。
pnpm run db:preflight:assets:worker --config=/absolute/private/wrangler.jsonc --local
pnpm run db:preflight:assets:worker --config=/absolute/private/wrangler.jsonc --remote
```

Windows 使用实际的绝对路径，例如 `--config="D:/private/one-gate/wrangler.production.jsonc"`。私有配置必须是 JSON/JSONC，顶层有唯一 `DB` 绑定、有效且非全零的 D1 ID，以及明确数据库名称。命名环境应先准备指向所需目标的独立私有配置；本工具不接受 `--env`，也不猜测继承后的资源。

工具拒绝无目标、相对配置路径、公开全零模板、重复/未知参数、任意 SQL、`--write`、`--reset` 和自定义迁移账本。不会创建远端资源、应用迁移、执行种子或清理数据。通过当前 Node 可执行文件和本仓库已安装的 Wrangler CLI 调用 `d1 execute --json`，不经 shell，也不自动下载安装软件。只输出固定元数据状态，不输出配置源、环境变量或提供方原始错误。

检查包括：

1. 7 张企业/资产表是否存在；不读取资产、企业成员或标识的业务内容。
2. Wrangler `d1_migrations` 是否记录 `0016_enterprise_assets.sql` 和 `0017_enterprise_asset_metadata.sql`。
3. 菜单 108/109 的路径、业务标识、父级 26 和启用状态，以及企业父菜单是否存在、启用且业务标识正确。
4. 7 项系统权限的存在、业务标识、类型和启用状态。
5. 平台角色 1 是否有效，以及是否有 7 项对应授权。

正常输出含 `reportVersion`、目标模式/数据库名称、`ready` 和 31 项检查。退出码 `0` 表示这些检查通过，`2` 表示缺项/冲突/禁用等发布前置条件不满足，`1` 表示参数、目标、查询或响应异常。缺失表时安全跳过依赖查询，并保留失败原因，不把查询失败当作空台账。

常见业务元数据分类为 `MENU_MISSING`、`MENU_CONFLICT`、`MENU_DISABLED`、`MENU_PARENT_UNAVAILABLE`、`PERMISSION_MISSING`、`PERMISSION_DISABLED`、`PLATFORM_ROLE_INACTIVE`、`ROLE_GRANT_MISSING`；迁移缺失与表结构缺失分别报告。工具仅报告，不恢复被管理员停用的菜单或权限，也不自动修复自定义配置冲突。

`d1-contract/enterprise-assets-metadata.sql` 是同一套只读诊断查询；单独执行 SQL 只返回诊断行，应以预检命令的退出码作为门禁。此预检不检查每列/索引/外键的完整定义，仍须运行 `worker-schema.sql` 结构契约；也不证明权限缓存、部署版本或在线功能正确。

本地目标可能由 Wrangler 创建本地模拟状态及日志；它们位于私有配置对应工作目录。`--remote` 才查询实际远端 D1。工具不会读取或打印应用 Secret；Cloudflare CLI 认证仍由操作者已有的私有认证配置负责。

## 既有 D1 资产版本上线顺序

1. 核对私有 Cloudflare 配置、实际 D1/Worker/三个 Pages 目标及本轮发布提交。公开配置是全零 ID 模板，不可直接用于生产。先预检并保存结果。
2. 备份并安排维护窗口暂停相关写入。确认远端当前迁移账本，再用同一批受审查代码应用剩余迁移；不要重新初始化旧库。当前站点账本仅至 `0014`，还须先运行角色坏引用预检，确认没有需要人工处理的旧引用后依次应用 `0015/0016/0017`。
3. 确认 `0016` 和 `0017` 均完成，运行完整结构契约和上述元数据预检。`0016` 负责新增 7 张表，`0017` 定向补两项菜单、7 权限、平台角色绑定及后端翻译，保留其他元数据。
4. D1 的两个迁移分别原子应用。若 `0017` 失败，`0016` 可能已完成；保持维护状态，解决冲突后继续余下迁移，不伪造账本成功记录。
5. 以同一提交发布 Worker、Admin、Enterprise、Personal。三个前端使用核对过的公开后端/远端模块 URL 构建；构建变量不放数据库密码或应用 Secret。
6. 按实际系统表单依赖同步系统 schema，显式失效线上权限缓存版本，再刷新菜单/权限或重新登录。直接执行 D1 SQL 不会自动更新 KV 缓存。
7. 先确认新菜单、实际页面、接口和部署版本，再用两家测试企业验收隔离、成员能力和只读 Token。全部通过后恢复相关写入。

当前超级管理员的菜单树不按角色权限过滤；其菜单缺失应优先核对真实菜单元数据和所连数据库，而不是只等待权限缓存。普通业务用户仍需系统权限与企业成员能力同时满足。

Node 旧 SQLite 库走 `db:migrate:assets:node --database=<现有本地文件绝对路径>`，它会在同一事务执行结构及元数据并记录校验值；本工具仅用于 D1。PostgreSQL 是另一条独立迁移路线，不能运行上述 SQLite/D1 SQL。

本轮工具的代码/测试与独立本地 D1 演练另行记录；仅在实际执行且结果可核对时标记通过。远端生产迁移、Worker/Pages 发布、缓存失效、Supabase 和线上业务验收均不得由本地测试结果推定。

本轮预检定向验证已完成：Node 29 项通过，其中使用已安装 Wrangler 在独立临时本地 D1 创建测试基础元数据、正式应用 0016/0017，再运行真实只读 transport；D1 Worker 元数据契约 2 项通过。脚本和 Node 测试的独立 strict TypeScript 无诊断，可格式化文件检查通过。完成 4 轮实现/测试复核，处理 Windows JSONC 错误路径、带前导注释的 CLI SQL 参数和真实迁移分段等边界；无远端写入。

另以当前站点的私有完整备份完成本地升级演练：先恢复到隔离 SQLite/D1 文件，再通过正式 Wrangler 本地迁移入口执行 `0015/0016/0017`，重复执行无待迁移，完整结构契约及元数据契约通过。62 张旧表的行数和规范化哈希、角色旧字段投影均保持一致；元数据仅新增 2 菜单、7 权限、7 个平台角色授权、30 条翻译及 3 条迁移记录，没有删除或覆盖旧元数据，新增的 7 张业务表为空。该结果是本地副本验证，不是远端导入或发布验收；整份备份直接通过 Wrangler 本地导入曾超时，未计入成功结果。

备份中的 `sqlite_sequence` 已有重复表名；演练仅在私有副本按每个表的 `MAX(seq)` 归一化后比较，43 个原有表的自增高水位与备份前只读快照一致且升级后无回退。该步骤没有修复线上序列；实际备份恢复演练也须核对序列高水位，不能只检查行数。备份内容和逐表校验报告含私人信息，保存在仓库外，不随代码公开。

后续可在私有发布流程中串联只读预检、备份/维护状态、迁移、结构及元数据门禁、同版本发布和验收证据；公开 CI 保持隔离，不引入生产凭据或远端写入。
