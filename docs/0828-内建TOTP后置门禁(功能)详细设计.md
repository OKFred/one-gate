# 内建 TOTP 后置门禁详细设计

## 1. 背景与目标

Hodor 当前由 Cloudflare Access 邮箱验证码保护浏览器入口。新的目标是在 `node_server`
内部提供兼容 Microsoft Authenticator、2FAS 等客户端的 RFC 6238 TOTP 二次门禁，并将
浏览器登录固定为：

1. 密码、GitHub、飞书或 one-sso 完成主认证；
2. 主认证只签发 Hodor Token，不加载菜单、权限或业务数据；
3. 输入部署级共享 TOTP；
4. TOTP Cookie 与当前用户和 Hodor Token 绑定后才允许进入系统。

本功能不修改 one-sso、不修改现有用户和 OAuth 绑定模型、不修改 D1 Schema，也不改变
设备回调、机器凭证和 WebSocket 的既有鉴权方式。

## 2. 分层与依赖方向

`admin/system/auth/totp-gate` 按垂直切片组织：

- `domain`：Base32、TOTP 参数、时间步、会话声明和错误码，不依赖 Hono、数据库或运行时。
- `application`：查询状态、验证验证码和签发门禁会话；只依赖 Clock、Secret、Crypto、
  Coordinator 等端口。
- `infrastructure`：Web Crypto、环境 Secret、Worker Durable Object、Node 内存协调器和默认装配。
- `interfaces/http`：POST Schema、Cookie、客户端摘要、Hodor 用户适配和 HTTP 错误映射。

应用宿主负责按请求解析 Worker 或 Node 运行时依赖。领域层和应用层不得读取 Hono Context、
Cloudflare Env 或全局请求状态。

## 3. 认证状态机

前端共享状态机包含四个阶段：

- `PRIMARY_AUTH_REQUIRED`：显示密码、GitHub、飞书、one-sso；微信入口保持 WIP。
- `PRIMARY_AUTH_CALLBACK`：处理 OAuth/SSO 登录回调，只保存 Hodor 用户和 Token。
- `TOTP_REQUIRED`：携带 Hodor Token 查询/验证门禁，不请求菜单和权限。
- `READY`：门禁状态与当前 Token 匹配后才加载用户、权限、菜单和业务路由。

登录回调不得在 TOTP 前加载菜单。账号绑定回调仍是登录后操作；若门禁在外部授权期间过期，
前端保留回调 URL，重新验证 TOTP 后重试回调。

非 admin 应用继续通过 gate 登录。返回地址必须匹配已配置的 admin、enterprise 或 personal
Origin；完成主认证和 TOTP 后才执行现有跨应用返回流程。

## 4. TOTP 与门禁会话

- 共享密钥由 20 字节 CSPRNG 生成并编码为 Base32。
- 使用 HMAC-SHA1、6 位、30 秒时间步，验证当前及前后各一个时间步。
- 每个成功匹配的时间步在协调器内只能消费一次。
- 每个匿名客户端每 60 秒最多 5 次失败，每个门禁部署每 60 秒最多 50 次失败；成功验证不占用失败额度。
- 生产 Cookie 名为 `__Host-hodor-totp-gate`，设置 `HttpOnly`、`Secure`、`SameSite=Lax`、
  `Path=/`；本地 HTTP 使用不带 `__Host-` 前缀的名称。
- Cookie 载荷包含版本、用户 ID、Hodor Token 的 HMAC 摘要、签发时间和过期时间，使用从
  TOTP 根密钥域分离派生的 HMAC-SHA256 密钥签名。
- 有效期为 24 小时且不得超过 Hodor Token 有效期。换账号、刷新 Token、重新登录、篡改
  Cookie 或轮换根密钥都会要求重新验证。

验证码、根密钥、Hodor Token 和 Cookie 均不得进入日志、错误响应、测试快照或 Git。

## 5. 协调与运行时

Worker 使用 SQLite-backed `TotpGateCoordinator` Durable Object。一个部署密钥指纹对应一个
逻辑协调对象，负责串行限流和时间步消费；对象只保存匿名客户端摘要、时间桶计数和近期已消费
时间步，并在请求中清理过期记录。

Node 本地运行时使用进程内协调器，具有相同接口和规则，仅用于开发与自动化测试。生产缺少
`HODOR_TOTP_GATE_SECRET` 或 Durable Object binding 时 fail closed；已有 Cookie 仍需根密钥
才能校验。

本次只追加 Wrangler Durable Object binding 和 class migration，不修改 D1 migration，不增加
外键。

## 6. HTTP 与路由策略

新增 POST 接口：

- `/api/v1/admin/system/auth/gate/status`：要求 Hodor Token，核对当前 Cookie 与 Token 绑定。
- `/api/v1/admin/system/auth/gate/verify`：要求 Hodor Token，验证 `{ code }` 并设置 Cookie。
- `/api/v1/admin/system/auth/gate/logout`：始终允许调用并清除 Cookie。

密码登录、OAuth/SSO 登录 URL 和登录回调、登录页翻译可在未通过 TOTP 时访问。TOTP 的
status/verify 绕过门禁中间件但不绕过 Hodor Token。账号绑定、用户资料、菜单、权限和业务
接口必须同时具有有效 Hodor Token 与匹配的门禁 Cookie。

OPTIONS、设备回调和上报、机器凭证接口及 WebSocket 继续绕过 TOTP。默认未知浏览器业务路由
必须要求门禁，避免新接口意外匿名开放。

## 7. 日志与错误

安全日志沿用 `requestId`，记录认证阶段、结果分类、用户 ID、provider、HTTP 状态和耗时；
匿名客户端只记录不可逆摘要，不记录原始 IP。

稳定错误码：

- `TOTP_GATE_REQUIRED`：门禁缺失、过期或与当前 Token 不匹配，HTTP 401。
- `TOTP_CODE_INVALID`：验证码错误、过期或已消费，HTTP 401。
- `TOTP_GATE_RATE_LIMITED`：触发限流，HTTP 429。
- `TOTP_GATE_UNAVAILABLE`：Secret 或协调器不可用，HTTP 503。

## 8. 部署与恢复

先生成忽略的本地登记文件和离线 QR 页面，再将同一生产密钥写入 GitHub Environment/Worker
Secret。代码发布后先保留 Cloudflare Access 做一次双层验收；确认 TOTP 全流程正常后导出
Hodor Access 应用和策略到忽略的本地备份，再删除仅属于 Hodor 的 Access 配置。one-sso
staging 等无关 Access 配置不在清理范围内。
