# 生产 D1 迁移闭环详细设计

## 1. 问题与证据

2026-08-12 生产 `hodor_db` 出现 Schema Drift：

- `admin_mobile_device` 只有旧的 9 列，Worker 已查询和写入 27 个设备上报列；新增设备、关键字检索、在线筛选和每分钟超时校正因此报 500。
- `admin_mobile_async_task` 只有旧的 13 列，协议、结果、优先级与抢占共 13 列均未迁移。
- GitHub Actions 直接发布新 Worker，没有 D1 迁移步骤。
- 旧 `db:init worker remote migration` 无迁移账本，每次重放全部 `ALTER TABLE`，单文件失败后继续并且最终返回成功。

## 2. 目标

- 数据库迁移在新 Worker 发布前执行，失败立即阻断发布。
- 使用 Cloudflare Wrangler 官方 D1 migration ledger，只执行未应用文件。
- 迁移后执行只读 Schema Contract，关键列或表缺失时禁止发布。
- 保留全量建表能力，但不再将它当作既有数据库的增量迁移。

## 3. 设计

### 3.1 迁移账本

`server/apps/server/d1-migrations` 作为 Worker D1 的唯一新迁移目录，并在 `wrangler.jsonc` 中配置 `migrations_dir`。

`0000_legacy_schema_baseline.sql` 是过渡基线：历史数据库先经一次性 reconciliation 和 Contract 校验，再由 Wrangler 记录该基线。新的增量变更只能 append 新文件，不修改已发布迁移。

Cloudflare 官方机制会记录已应用文件，迁移失败时回滚当前迁移并返回非零状态：

- https://developers.cloudflare.com/d1/reference/migrations/
- https://developers.cloudflare.com/d1/wrangler-commands/

### 3.2 Schema Contract

`d1-contract/worker-schema.sql` 仅执行 `SELECT ... LIMIT 0`，覆盖：

- `admin_mobile_device` 完整 36 列；
- `admin_mobile_device_event` 完整列；
- `admin_mobile_async_task` 完整 26 列；
- `system_schema_form.source`；
- 设备心跳/状态索引及设备事件的三个索引。

任一列或表缺失都会使 Wrangler 命令失败，防止空列表 200 掩盖真实漂移。

### 3.3 发布顺序

1. 安装后端依赖。
2. `wrangler d1 migrations apply hodor_db --remote`。
3. 执行只读 D1 Schema Contract。
4. 发布 Worker。
5. 同步系统 Schema 数据。
6. 构建并发布 Pages。

Worker 发布步骤同时注入 `JWT_SECRET` 与 `MOBILE_SENSITIVE_DATA_KEY`。后者缺失时应在部署阶段失败，避免敏感设备元数据上报运行到生产后才报错。

## 4. 兼容与非目标

- 不修改 HTTP/MQTT 协议、业务表数据或管理页行为。
- 不重放、不改写已发布的 legacy migration。
- 新建空 D1 仍先使用全量 `db:init worker remote`创建当前表，然后应用官方 migrations 并运行 Contract。
- 安全结构化 SQL cause 日志属于后续可观测性增强，不向 HTTP 500 响应泄漏 SQL 或参数。
