# 数据库迁移脚本清理实际落地

## 实际改动与计划对照

本轮在 `codex/postgresql-support` 分支继续处理工具清理，保留此前 PostgreSQL 实现，没有提交、推送或部署。

- 全量 DDL 生成器不再清空迁移目录，不再生成无账本增量 SQL；改用已安装的 Drizzle CLI 和独立临时目录。三个领域全部生成、解析与输出路径检查成功后才写入新库 DDL，失败返回非零。拒绝输出路径经过符号链接或目录连接，拒绝越界表名；生成器不连接数据库。
- `db:init node migration` 在配置加载、数据库操作及种子同步前拒绝执行，并指向受控命令。Node 全量初始化按需导入数据库模块，结构失败即停止种子；移除为 `system_schema_form.source` 补列的一次性逻辑。`baseTableInit` 增加显式严格选项，现有其他调用保留默认行为。
- Worker 全量初始化中的不可达旧增量分支已移除。兼容 migration 参数继续走官方 Wrangler 账本，不同步种子。
- 保留 25 份 legacy SQLite、19 份 D1 和 1 份 PostgreSQL 编号 SQL，以及三个 Node 专项迁移工具。历史目录增加用途说明；根目录、后端和部署说明链接统一迁移指南。

与计划一致。参数解析留在 `initTable.ts`，没有额外增加参数模块；新增参数歧义、环境文件、严格错误测试。除计划内行为外没有引入新的迁移框架，也没有对历史 SQL 做合并、删除或重编号。

实际新库演练的验证进程关闭 libSQL 后，Windows 仍短暂保留原生文件句柄，辅助脚本清理临时目录报 `EPERM`；产品初始化命令本身已成功。随后自动审批以策略限制拒绝删除该演练临时目录，未提供更具体原因，目录保留。没有重试被拒绝的删除，没有影响用户数据库或其他容器。

## 限制与后续建议

全量 DDL 输出不是文件事务：所有领域生成成功后，写入阶段若发生磁盘或权限错误，可能留下部分新 DDL，命令会返回失败。此时检查 Git 差异并恢复受影响生成文件，不能执行数据库初始化来处理生成错误。源码生成与实际数据库修改始终分开。

根目录原有 TypeScript 诊断分别位于 mobile app-version、app、async-task 的 repository，以及两个旧移动设备验证脚本；本轮未扩展修复范围，没有新增待决策诊断。后续若要压缩历史迁移，应单独设计新库基线和存量版本截止点；不应通过删除当前账本文件实现。
