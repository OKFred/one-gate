# 回收站可靠性详细设计

## 背景与范围

上一轮通用回收站已由 PR #106 合入 dev 并发布，首期接入部门。本轮用户选择“完善现有机制：清理可观测性、边界和测试”，从最新 dev `d1e8be51` 创建 `codex/recycle-bin-hardening`。

本轮解决三个已观察到的问题：空清理轮次缺少逐资源完成证据；Workers 测试发现沿工作区链接重复收集且混入 Node 专属测试；同资源分页或搜索失败时，页面保留旧记录却显示新的查询状态。继续沿用注册表、业务适配器、30 天保留期与条件 SQL。

## 清理结果日志

公共执行器对每个显式注册适配器输出一次结构化结果。成功的空轮次也记录 info；仍有到期积压时记录 warn；适配器失败记录不含底层错误文本的 error，然后继续其他资源，最后让本轮调度失败并在下分钟重试。

固定日志字段包含资源标识、检查时间、到期截点、已清理数量、剩余到期数量、最早到期时间、最大超期时长和耗时。使用显式字段选择，禁止展开适配器结果，避免将业务附加字段或实体内容写入日志。错误事件使用固定错误码，不记录 SQL、参数、记录名称或异常堆栈。

统计值要求非负安全整数；每类实际删除数不能超过公共批量上限；积压为零时最早到期时间为空，有积压时应为不晚于本轮检查时间的有效 UTC 毫秒。异常统计按适配器故障处理，不能作为成功指标。统计是清理之后的一次观察，不声称跨并发执行具有事务快照一致性。

采用现有 console 结构化日志与 Worker/Node 调度，不新增数据库表、日志存储、定时配置或外部通知服务。日志查询说明区分“任务被触发”“资源完成检查”“实际删除记录”；缺少日志可能与执行失败或日志采集有关，不单凭沉默推断正常。

## 页面查询边界

列表结果必须对应当前已成功加载的查询。开始新的分页、搜索或刷新请求时清理旧结果及旧选择；加载和失败状态不允许对旧记录操作。错误提示继续复用公共 HTTP 层和现有页面重试提示。

恢复或清除成功后若刷新失败，已操作记录不能留在可操作列表中。请求失败本身仍保留当前查询，允许重试；变更请求失败时继续保留原确认记录和删除版本，以显示明确冲突。分页在结果未就绪时不得显示旧总数和误导性范围。

本轮不扩展服务端时间接口。客户端时钟偏移造成的显示差异列为后续增强，服务端 30 天期限检查始终是最终依据。

## 测试发现与数据边界

Workers 配置只从应用源码及明确的业务包源码根目录发现测试，保留共享测试与 Workers 专属测试，排除 Node 专属测试和 node_modules 链接路径。通过仅列举的发现结果核对物理路径去重与运行时分类，再执行本轮相关测试，避免用重复执行次数替代用例覆盖数。

部门和历史归档继续使用原有状态、期限与引用条件删除。补充验证被引用的到期记录不会阻塞后续可删除记录、精确到期边界与重复批次、失败恢复及日志隐私边界；若已有用例覆盖则复用，不制造同义测试。

## 验证与交付

改动前后比较服务应用、后端根配置和管理端 TypeScript；变更文件执行 ESLint/Prettier。完成至少两轮独立复核，复核修改遵循仓库先暂存再修正流程，最终执行 git diff --check。

交付分别记录代码测试、数据库测试和线上验收，不将本地测试当作生产完成。此次没有新增迁移；沿用上一轮 Git/CI/发布流程时，线上核对版本、聚合计数与精确版本的逐资源空轮结果，避免为日志验收制造生产删除数据。
