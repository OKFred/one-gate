# 私人日历详细设计

## 范围与首条日程

新增独立私人日历 `/calendar`，首页仅增加日历快捷入口，不恢复首页长列表。月历、选中日期的日程与接下来 5 条日程支持新增、编辑和取消。仅站内提醒，不创建 Codex 自动化、邮件、系统推送或周期任务。

首条真实日程在上线后通过当前登录账号接口创建。用户提供的标题、具体时间和链接仅保存在私人日历及仓库外验收材料，不写入公共代码、测试或迁移种子。时间按用户确认的北京时间转换为 UTC 毫秒；链接仅保存，不抓取、不代办续约。

## 数据与 API 合同

新增一表 `personal_calendar_event`，SQLite/D1 与 PostgreSQL 对应模型：UUID id、ownerUserId、requestKey（按 owner 唯一，用于创建幂等）、title、可空 description/url/endTimeUtc、startTimeUtc、timeZone、可空 reminderTimeUtc/reminderAcknowledgedTimeUtc、status(active/cancelled)、version、createTimeUtc/updateTimeUtc。时间为 UTC 毫秒，所有非创建时间字段无数据库默认值，新增时服务显式赋值。仅支持一次性日程，取消后保留记录但不再显示或提醒，不接入管理员回收站。

全部接口为 POST，前缀 `/api/v1/personal/calendar`，要求已登录且通过既有安全门禁的人类用户。owner 只取 principal.userId，不接受请求传 userId；超级管理员同样不能访问别人的私人日程，API Token 拒绝。

- `list {fromTimeUtc,toTimeUtc}`：返回 `{list,hasMore,upcoming}`；区间最多 93 天，列表最多 500，另返回接下来 5 条。截断时界面明确提示并支持选单日缩小范围。
- `get {id}`：返回本人事件。
- `add {requestKey,title,description?,url?,startTimeUtc,endTimeUtc?,timeZone,reminderTimeUtc?}`：返回事件。同用户相同 requestKey 不重复新增；冲突请求不得覆盖原记录。
- `update {id,expectedVersion,...完整可编辑字段}`：返回事件；以 owner/id/version 条件更新并递增版本。
- `cancel {id,expectedVersion}`：返回原 id；条件更新 cancelled 状态，不硬删除。
- `due {}`：返回 `{list,hasMore,nextReminderTimeUtc,serverTimeUtc}`，最多 20 条到期未确认提醒；只读，不因显示自动确认。
- `ack {id,expectedVersion,expectedReminderTimeUtc}`：返回 `{id,acknowledgedTimeUtc}`；仅确认原提醒，重复确认幂等成功，改期或取消后旧请求冲突。ack 不递增事件编辑版本；编辑用条件 SQL 保留未改期提醒的确认状态，改期才重置，避免覆盖并发确认。

校验标题/说明长度、有限整数时间、结束不早于开始、提醒不晚于开始、合法时区和 http/https 链接；不返回 SQL、凭据或他人记录。使用稳定业务码及明确 400/404/409 状态。

## 站内提醒

提醒宿主只挂在已登录且完成安全验证的管理端布局内。页面可见时至多每分钟只读检查，并依据服务端时间和下次提醒时间安排到点检查；隐藏时停止轮询，重新可见或日程更改后立即同步。只显示一个紧凑提醒和“查看日历/知道了”；确认收到成功才移除，不自动重试写操作。

退出、换账号及迟到响应必须隔离，取消或修改后的旧提醒不得确认新版本。关闭站点时不会发后台/系统通知，期间到期的事件在下次打开时显示待处理。提醒失败使用局部状态，避免每分钟全局重复弹错；不新增 Cron、队列、邮件或外部消息。
