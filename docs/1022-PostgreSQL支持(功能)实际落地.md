# PostgreSQL 可选后端实际落地

## 交付状态

2026-10-22，基于 `main@346f09bf`，开发分支 `codex/postgresql-support`。本轮已完成 PostgreSQL 首期身份权限、企业资产及软删除闭环，保留现有 Node SQLite/libSQL 和 Worker D1。改动覆盖 107 个以上文件，包括 PG schema、仓库、运行时、迁移、种子、测试和运维说明；最终文件集合以提交前的 Git 差异为准。

截至本文更新，代码尚未 commit、push、建立 PR 或合并，也未对 gate 生产环境执行迁移或发布。Supabase 的隔离验证已完成连接、迁移、基础元数据种子及真实 Node HTTP 验收；云端 Worker → Hyperdrive → Supabase 尚未验收。

业务适配依赖标准 PostgreSQL、Drizzle 与 `pg`，不绑定 Supabase 的专有业务 API。托管 Supabase 仅为本轮验证提供方；自托管 Supabase、其他 PostgreSQL 提供方及私网连接留在部署配置边界。本期没有实现 Zero Trust、Tunnel 接入或相关网络策略。

实施前决策保存在[详细设计](<./1022-PostgreSQL支持(功能)详细设计.md>)和[计划变更](<./1022-PostgreSQL支持(功能)计划变更.md>)。本文件记录实际结果，不把构建、本地模拟和线上验收混为一项。

## 已完成的能力

### 25 张首期 PG 表与独立迁移

首期 PG DDL 建立 25 张表：

| 范围                 | 表                                                                                                                                                                                                             |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 写入协调             | `one_gate_write_guard`                                                                                                                                                                                         |
| 身份、权限及导航     | `system_user`、`system_role`、`system_department`、`system_permission`、`system_role_permission`、`system_api_token`、`system_menu`                                                                            |
| 国际化               | `i18n_language`、`i18n_region`、`i18n_translation`                                                                                                                                                             |
| 配置、日志及历史归档 | `base_sys_config`、`base_user_config`、`base_sys_log`、`base_audit_log`、`base_biz_log`、`base_http_request_log`、`compliance_archives`                                                                        |
| 企业与资产           | `enterprise_tenant`、`enterprise_tenant_member`、`enterprise_tenant_api_token_grant`、`enterprise_asset`、`enterprise_asset_identifier`、`enterprise_asset_assignment`、`enterprise_asset_measurement_binding` |

PG schema 使用真正的 `pgTable`、原生 boolean、jsonb、安全整数及 UTC 毫秒字段。对外 DTO 和 API 合同继续复用原模型；没有把 SQLite 表强转成 PG 表，也没有把全仓业务表一次迁移到 PG。

PG 使用独立编号迁移及校验值账本，具备事务、重复执行保护和失败回滚。既有 D1 迁移历史保持独立。基础种子采用定向补充策略，不重置现存用户密码或清空自定义菜单、权限。元数据准备完成仍可能返回 `pending_admin`，不能将它解释为已有可用管理员。

### Node、Worker 与数据库作用域

Node PG 使用有界 `pg.Pool`；Worker PG 在每次 fetch/scheduled 生命周期建立独立连接并释放，后台任务保留对应数据库上下文。事务内显式设置目标 schema 的 `search_path`，不依赖池化连接保留会话状态。

选择 PG 后，缺少配置、绑定、作用域或受支持能力时明确失败，禁止静默访问 SQLite/D1。Worker PG 配置要求关闭 Hyperdrive 查询缓存；本地验证不能证明线上 Hyperdrive 的配置及连接链路已正确建立。

### 身份权限、企业资产及软删除

- 密码登录、JWT、TOTP 门禁、profile、当前角色权限和菜单树通过 PG 闭环；API Token 保留独立机器身份，不继承创建人的管理员身份。
- 用户、角色、部门引用和权限撤回在 PG 中验证；缓存命中不能代替最终数据库权限条件。
- 企业独立台账、成员能力、最后 owner、企业冻结及恢复、资产标识、安装历史和测点绑定均有 PG 仓库实现。机器 Token 只允许显式企业授权的最小映射查询。
- 部门与角色的软删除、15 秒撤销、30 天恢复窗口、回收站恢复、超级管理员提前清除及到期清理已接入 PG。撤销仍要求本次删除人及当前删除权限，保留删除版本、名称、父级、引用和执行时限约束。
- JSON 配置、国际化和通用日志使用 PG 查询。系统/业务日志的 JSON 条件、类型匹配及参数绑定已通过真实 PG 测试；个人配置按归属人隔离。

本轮没有改变原 API 的浏览器登录和二次验证交互，也没有把身份系统迁移至 Supabase Auth。

## 实际采用的保守策略与范围差异

### 公共写入 guard

首期所有 PG 关键写事务先锁定公共 `one_gate_write_guard(id=1)`，随后在同一事务重查身份、权限、企业和记录版本。它为跨身份及业务引用提供与既有单写者机制接近的安全边界，代价是所有企业写入共享一个锁，写入吞吐受限。细分身份锁、企业锁是后续优化，本轮不宣称已经实现多企业并行写入扩展。

15 秒撤销使用数据库实际执行时刻判定，锁等待不能延长撤销资格；30 天仍从原删除时刻计算。数据库明确回滚与客户端结果未知分开处理，不自动重试无法确认结果的外部写请求。

### 能力门禁及配置事务

PG 在业务路由前应用独立允许清单。未适配能力返回 `POSTGRESQL_CAPABILITY_UNAVAILABLE`、HTTP 501，避免进入 SQLite/D1 仓库或启动旧后台任务。

SSO、邮件、移动设备、RPA、MQTT、业务 Cron 等首期不开放。PG 仍执行公共到期清理调度，业务 Cron 未开放不影响该机制；登录的非必要邮件通知也不会启动未适配邮件链路。

配置操作补入事务范围，失败须回滚包括主配置标记在内的关联修改。测试覆盖事务失败后数据保持一致，不能只以单条更新成功作为整体成功。

## 真实运行与提供方验证

### 本地 Worker + PG

已通过本地真实 workerd 验收：21 次 HTTP 请求覆盖登录、TOTP、部门删除与撤销、企业资产、企业隔离及未支持接口 501；另执行 scheduled 到期清理并核对结果。验收使用独立私有 schema，汇总中的相应结果均为成功。

这证明本地 Worker 运行时的实际驱动与业务链路可执行，不等同于已发布的云端 Worker、线上 Hyperdrive 或 gate 生产环境。

### Supabase

已在用户指定项目建立专用数据库角色及隔离验证 schema，未使用其他项目业务表承载本轮数据。已确认 PostgreSQL 17.6 和 TLS 连接；编号迁移首次为 `applied`，重复为 `already_applied`。基础元数据种子曾返回 `pending_admin`，随后显式建立随机合成管理员完成验收，其凭据仅保留在仓库外私有配置。

通过实际 `src/node.ts` 入口，在本地回环地址启动 Node 服务，经 TLS 访问 Supabase PG 17.6，完成 21 次 HTTP 请求：登录、实际 TOTP、部门删除与撤销、两家企业的资产闭环及隔离、未支持接口 501 均通过。本次合成企业、成员、资产等业务测试记录已清理，随机合成管理员保留供后续验证；没有把其用户名、密码或 Token 写入公开产物。

提供方隔离复核确认，非 One Gate 的 56 个 relation 的名称、类型和所有者目录保持完全一致；专用角色对 `public` 的 4 张表 CRUD 权限均为 false。重复迁移结果为 `already_applied`。角色仅获新 schema 所需的 `USAGE/CREATE` 与本轮对象访问权限，不具备数据库级 `CREATE`、`CREATEROLE` 或 `BYPASSRLS`。

云端 Worker → Hyperdrive → Supabase 的连接、查询缓存关闭及实际权限链路尚未验收，不能因本地或 Node 远端验收通过而标记完成。连接串、密码、私有凭据和业务记录不进入文档或公开日志。

## gate 并行诊断与发布准备

公开静态资源及版本只读核对确认：`gate.this-time.com` 的 API 为 `hodor.this-time.com`，Admin、Enterprise、Personal 与 API 四端均仍为 `20260919193143-db2a14fc`。线上缺少企业/资产菜单，生产迁移账本仅至 `0014`，合并公开仓库 `main` 不会触发旧私有发布流程。

本轮新增默认只读的资产发布预检，要求绝对私有 Wrangler 配置及显式 `--local` 或 `--remote`，拒绝全零模板和任意 SQL。31 项检查只读取结构、迁移及菜单/RBAC 元数据，不读取企业资产业务内容。`db:init node` 只作用于本地 SQLite；现有全量非 reset 种子也可能删除、覆盖自定义配置，因此没有将它用作线上补菜单捷径。

已导出生产完整备份，并在私有副本完成 `0015/0016/0017` 的真实本地 D1 迁移演练。角色坏引用预检 7 项均为 0；62 张旧表的行数及规范化哈希、角色旧字段投影保持一致；43 个原有表按 `MAX(seq)` 比较的自增高水位无回退。新增元数据仅为 2 菜单、7 权限、7 个平台角色授权、30 条翻译和 3 条账本记录，没有删除或覆盖旧元数据，7 张新业务表为空。完整结构和元数据契约均通过，重复迁移无待执行项。

备份原有序列中存在重复表名，演练仅在副本核对并归一化高水位，没有修复线上序列。整份备份直接经 Wrangler 本地导入曾超时；通过隔离文件恢复后再执行正式本地迁移的结果，不能被写成远端导入成功。

生产迁移、Worker/三个前端发布、缓存失效及线上资产验收尚未执行。具体命令、环境区别和升级顺序见[gate 发布与种子同步](<./1022-gate发布与种子(运维)说明.md>)。PG 支持不构成 D1 资产功能发布的依赖。
