# AutoJS6 重复部署阻断优化详细设计

## 背景

设备完成部署后，管理页的部署历史和设备心跳快照可能在不同轮询周期到达。操作者在页面尚未刷新时再次点击同一目标，会创建一个没有实际状态变化的部署记录，增加无意义的下载、重启和审计噪音。

## 目标

1. Node Server 在写入部署记录和下发 MQTT 命令前，拒绝设备当前已经运行的目标组合。
2. 普通部署和回滚使用同一判定规则。
3. 管理页展示设备心跳中的当前组合，并禁用明显的重复部署或重复回滚操作。
4. 页面内所有部署和回滚提交共用同步互斥锁，避免 React 状态刷新前的快速重复点击。

## 权威状态与判定

设备心跳 `reportedExtra.deployment` 是当前实际运行组合的权威快照。目标与当前状态仅在以下字段全部相等时视为无变化：

- `releaseVersion`
- `releaseDigest`
- `environment`
- `environmentRevision`

摘要不一致时仍允许重新部署，用于修复同版本目录异常或设备侧内容损坏。心跳缺失、格式非法或字段不完整时不做无变化推断，继续执行既有部署流程和健康检查。

## 服务端边界

`apply` 和 `rollback` 在完成设备、发布版本和环境修订解析后，先比较当前组合与目标组合。相同时返回统一的 `VALIDATION_FAILED` 业务错误，不创建 `client_deployment` 记录、不生成制品下载地址，也不发布 MQTT 命令。

既有“单设备只能有一个未终结部署”约束保持不变，继续处理并发请求和部署中的互斥；无变化校验处理上一部署已经终结后的重复请求。

## 前端交互

部署页轮询发布版本、环境修订、部署历史和设备详情。页面根据设备详情中的当前组合：

- 在目标与当前组合相同时显示说明并禁用“开始部署”；
- 在部署尚未终结时禁用新的部署和回滚；
- 最新部署终结后先按其结果推导当前组合，避免等待下一次设备心跳时出现短暂重复入口；
- 在回滚目标与当前组合相同时禁用对应回滚按钮；
- 部署或回滚确认开始前同步取得页面级提交锁，完成刷新后释放；
- 请求期间禁用全部部署和回滚入口。

前端预判仅改善交互，不能替代服务端校验。

## 验证

- 单元测试覆盖完整匹配、摘要不一致、环境/修订不一致和非法心跳。
- Server 格式化、类型检查、测试和构建通过。
- Platform 格式化、类型检查、构建、原生弹窗扫描和 lint 检查通过。
- 生产页面选择设备当前的 `v2.1.7 / production / r1` 时按钮禁用。
- 直接调用生产 apply 接口返回无变化错误，部署历史数量不增加。

## 发布版本盖章

生产验收发现 pre-commit 在新提交产生前读取 `HEAD`，导致 Pages 的 `version.json` 永远标记上一个提交。发布工作流改为在 Worker 部署和 Pages 构建之前，使用同一个 `${github.sha}` 和时间戳同时盖章 Wrangler `VERSION` 与三套 Pages 共用的静态版本文件。本地仓库保留 `local-development` 占位值，pre-commit 不再提交不准确的旧 SHA。
