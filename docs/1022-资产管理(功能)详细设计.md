# 多企业资产管理详细设计

## 状态与基线

2026-10-22，角色软删除已通过 PR #1 合入 `main`（`9bc9972dd7975b63aab19e8d5b77d32504bbf629`）。从该提交建立 `codex/enterprise-assets`，本文件是资产功能的实施前设计，不代表功能已实现或生产数据已迁移。

用户明确要求资产管理归属 `enterprise`，且多个企业分别维护独立台账。业务来源是设备身份及温度采集映射：同一硬盘换主机后身份不变，历史读数按当时的安装与测点关系解析，设备不一定具有可信 SN。

## 首期范围

交付企业和成员基础、硬件台账、硬件标识、安装/迁移历史、测点映射和只读解析能力。首期覆盖主机、硬盘、GPU、板卡、传感器、电表等实物资产。

One Gate 作为资产信息唯一维护入口与主库，继续支持 Node SQLite/libsql 和 Worker D1。IoT 项目的 PG、Supabase 和采集端可以保存带企业范围的只读投影或缓存；原始遥测、MQTT 采集和七天遥测保留不迁入 One Gate。此前另一个线程中“PG 作为资产主库”是助手建议，本设计依据本次产品归属调整，不建设两套可各自修改的主台账。

采购、折旧、财务账套、自动硬件发现、跨企业资产转让、SSO 自动入企、邮件邀请和实际 PG/MQTT 同步暂不纳入首期。现有考勤、工作流、EDM 也不随本期自动取得企业隔离能力。

## 当前仓库的接入缺口

- `enterprise` 当前是应用与包分组，没有本地企业/成员权威关系；已有邮件、日志或 SSO 的 `tenant_id` 不可直接当作企业授权。
- 全局 RBAC 和 `dataScope` 不会自动过滤企业资产查询；创建人或系统部门也不是企业归属。
- API Token 的 `userId/id` 当前采用创建者 ID，鉴权对象没有可信主体类型和 Token ID。直接套成员检查会错误地让 Token 继承创建者的所有企业。
- 通用回收站、删除收据、撤销调用和资源通知尚无企业 scope。同账号切企业不会变更登录会话，不能直接注册资产适配器并沿用全局后台入口。

## 企业与授权基础

企业由当前登录的平台超级管理员创建，并在同一原子操作中设置首位 owner。企业 key 不复用；企业启停由平台管理，停用保留全部资料与历史。

企业内角色采用固定能力集合 `owner/admin/editor/viewer`，与系统角色 ID 分离。系统 RBAC 决定是否开放功能，企业成员关系决定本企业中的实际能力，两者共同满足才放行。人类用户的普通资产接口始终要求明确企业与有效成员，平台超级管理员也不能使查询省略企业条件；平台管理操作使用明确入口和审计。机器只读接口按可信 `api_token` 主体及显式企业 grant 授权，不走创建者的成员检查。

owner 管理成员和所有者交接；admin 不得授予 owner、修改 owner 或提升自身能力。企业成员管理入口不能使最后一名有效 owner 退出、停用或降级；有效性同时考虑成员状态与关联系统用户是否可用，交接原子执行。若全局用户管理另行停用或删除账号导致无可登录 owner，企业常规访问按当前数据库条件冻结（含机器读取），由平台超级管理员通过显式恢复/接管入口处理并记录审计；不承诺企业成员入口能拦截全部全局身份变化。成员首期引用既有系统用户，不提供全站用户目录搜索，不把 SSO 外部企业标识自动转成本地成员关系。

鉴权层由服务端构造判别联合：`{kind: "user", userId}` 或 `{kind: "api_token", tokenId}`。请求不能覆盖主体；core 只提供认证后的身份，企业授权由企业包处理，不让 core 反向依赖资产业务。

## 数据模型

所有时间为 UTC 毫秒；新增列不使用数据库默认值，创建时间沿用仓库已有规范。系统状态和审计字段由服务端显式赋值。

| 表                                     | 主要职责与约束                                                                                                        |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `enterprise_tenant`                    | 企业 key、名称、启用状态、版本和审计；不复用停用企业 key                                                              |
| `enterprise_tenant_member`             | `(tenant_id, user_id)` 唯一；角色、启用状态、版本和审计                                                               |
| `enterprise_asset`                     | 数值内部 ID、服务端生成且不可变的全局 `asset_id`、不可变 `tenant_id`、名称、类别、品牌型号、在用/退役状态、版本和审计 |
| `enterprise_asset_identifier`          | 企业、资产、标识类型、命名空间、原值/标准化值、来源、可信度与核验状态                                                 |
| `enterprise_asset_assignment`          | 企业内资产与承载主机/位置的安装关系、UTC 有效区间、版本和变更原因                                                     |
| `enterprise_asset_measurement_binding` | 企业、来源系统、采集器、设备、指标、通道到资产的时效映射                                                              |
| `enterprise_tenant_api_token_grant`    | Token 显式绑定一个企业、只读映射能力、启用状态及审计；Token 不继承创建者成员资格                                      |

资产名称允许重复。人工资产编号如提供，则按企业唯一；`asset_id` 不因改名、换主机或退役改变。普通新增/编辑 DTO 不接受系统 ID、企业归属、版本推进值和审计字段的任意覆盖。

SN、WWN、GPU UUID、SID 是不同类型的身份依据。缺少 SN 可以正常建档；`N/A`、全零、OEM 占位等不能当有效标识。保留原始值，标准化按类型定义，不能一律去除符号后猜测相同设备。已核验强标识按企业、类型、命名空间、标准化值建立唯一约束；未核验弱证据不自动合并资产。两家企业使用相同 SN 或测点名称互不冲突。

## 数据库中的企业边界

请求可以表达用户选择的企业，但必须先形成已验证的 `TenantContext`。repository 必须接收上下文，避免无范围的 `findById(id)`。普通编辑不能改变已有记录的企业。

列表、总数、详情、搜索、标识查找、选择器、历史与映射解析都包含企业条件和当前授权。新增使用带存在性条件的 `INSERT ... SELECT`；更新包含企业、记录 ID、预期版本以及数据库当前企业/成员状态。不能仅在 service 检查成员后执行无条件写入。

资产与标识、安装、测点绑定的关联必须同企业；承载主机也必须是本企业有效资产。复合唯一和复合外键作为额外防线，最终写 SQL 仍重复同企业与有效性条件。并发停用企业、撤回成员或撤回机器授权后，排队请求不能凭旧缓存成功写入。

不可见和不存在的业务记录返回一致的不可见结果，不暴露其他企业的名称、SN、归属或数量。首期不允许修改 `tenant_id` 来划转资产；跨企业转让需要单独定义历史可见性。

## 安装、迁移与历史解析

安装关系与测点映射分开保存。区间采用 `[validFromUtc, validToUtc)`；同企业同资产不能存在重叠的安装区间，同企业同来源/采集器/设备/指标/通道也不能有歧义映射。重叠检查覆盖历史区间，不能只检查“当前未结束”记录。首期不支持未来生效排程，新关系的起点不能晚于数据库执行时刻；历史纠错仍需版本、原因和区间检查，退役不会留下将来自动生效的关系。

换主机时保留 `asset_id`，原子地结束旧关系并建立新关系；最终 SQL 校验预期版本、同企业、成员能力、关联状态和区间冲突。绑定历史不开放无提示覆盖原归属的普通编辑；纠错需版本与原因，保留可追溯记录。批次内的零行变更不能直接当作成功，Node 和真实 D1 都要验证无部分提交。

解析按原始 `observedTimeUtc` 匹配当时区间。离线补报不能使用当前所在主机倒挂历史；缺少映射、歧义或无权访问时明确返回，禁止猜测或自动创建资产。一条主机消息包含多件硬件时按指标/通道分别解析；CPU/GPU 温度测点不虚构独立厂家 SN。

## 生命周期与回收站

首期提供在用、退役及显式重新启用。退役原子结束当前安装/测点关系，保留资产身份与历史；重新启用不自动重开过去关系。旧读数仍可按观测时间解析。

首期不提供资产硬删除、30 天物理清除或全局回收站接入，避免破坏历史连续性。此前部门和角色的 30 天回收站维持原行为。以后需要误建删除时，应先定义企业范围的收据、恢复/撤销、通知与清理合同，以及有历史引用时的身份保留规则，不能通过“退役等于删除”绕过历史保护。

## 采集端只读能力

复用现有 API Token 认证，增加显式企业 grant；未配置企业授权的旧 Token 即使有资产权限也拒绝。Token 只能解析/读取被授权企业的映射，不能管理企业、成员或资产。令牌状态、有效期、权限、企业状态和 grant 状态共同生效，撤回后线上请求重新校验。

grant 管理由本企业有管理能力的人操作，仅可绑定本人创建、当前可用且未绑定其他企业的 Token；不接受任意他人 `tokenId`，不返回 Token 原文或哈希。创建者 ID 在这里仅证明 Token 管理资格及审计来源，绑定后的运行授权以显式 grant 为准。默认每个 Token 只绑定一个企业，禁止通过更换请求企业借用创建者的其他成员关系；只读解析仅返回必要资产身份与通道信息，不额外暴露 SN 等管理资料。

采集端缓存和将来导出投影都带企业维度、来源键、区间和版本；不能只按来源字符串建立全局映射。本期交付只读合同及本地验收，不修改另一仓库的生产采集、PG 或 Supabase。

## 接口、页面和仓库接点

所有业务接口使用 POST，位于 `/api/v1/enterprise`。建议按 `tenant`（企业/成员/令牌授权）和 `asset`（台账/标识/安装/测点/解析）组织领域，字段集中定义在 model，service 导出 API 对象，同级 index 挂载。

前端以平铺的 `/enterprise/tenant`、`/enterprise/asset` 页面接入。台账有明确企业选择器、名称/类型/状态搜索和分页，详情展示身份依据、安装历史与测点绑定。企业切换清理列表、详情、表单与确认框，并推进独立 scope epoch；同账号 A→B→A 的旧响应不能写入新页面。普通 CRUD 使用包含企业的 `resourceKey`，不借用无企业 scope 的软删除配置。

后端代码位于 `server/packages/enterprise/src/{tenant,asset}/`，由包根入口挂载。跨包的用户及 Token 元数据查询通过 admin registry 的明确接口提供，不直接引用其他包的私有 repository/service。

权限源为 `server/packages/core/src/constants/permissions.ts`；同步业务类型、菜单及后端错误翻译，再运行生成链更新前端权限常量、页面 constant 和 OpenAPI。页面中英文文案写入 enterprise 的本地 locale，不写入后端翻译表冒充页面文案。

## DDL 维护工具补充设计（2026-10-22）

资产功能交付后的继续迭代将临时生成步骤收敛到仓库内。增加专用 `server/scripts/generate-enterprise-assets.ts`，从当前 tenant/asset 模型及本仓库锁定的 Drizzle Kit 在全新临时目录生成快照，不接受工作区之外的旧快照或硬编码机器路径。

默认只检查模型与现有产物是否一致，差异以非零退出状态及文件名报告。显式 `--write` 仅更新 7 份新库 DDL、独立资产结构契约和部署契约中的唯一资产段；0016/0017 及历史迁移目录均不改写。今后结构变化仍需新增编号迁移，生成工具不连接数据库。

生成结果先校验完整表白名单、无数据库默认值、可支持的 SQL/快照结构及契约标记，再进行文件操作；拒绝符号链接或非普通文件目标。受控写入异常恢复已改动文件，不能将多文件写入宣称为断电或进程崩溃级原子事务。临时目录清理限定为工具本次创建的目录。
