# 通用回收站详细设计

## 背景与范围

部门软删除与 30 天回收站已合入 dev。本次从最新 dev（919e0fa6）创建 `codex/recycle-bin-registry`，将回收站接口、页面和清理注册改为业务无关机制。首期仍只注册部门，其他业务表不迁移，不复制完整记录到集中快照表。

## 分层与接入

- core 定义资源适配器合同和显式注册表，提供公共字段、固定 30 天保留期和清理执行器，不导入业务包。
- 应用组合入口显式注册部门适配器。注册表仅接受声明的逻辑资源键，拒绝重复冲突注册；接口不解析物理表名，不扫描数据库发现资源。
- 业务适配器提供资源键、展示翻译键、权限判定、已删除记录查询、恢复、彻底删除和到期清理方法。所有交互方法获得当前登录用户，业务模块负责数据可见范围和写入范围。
- 部门适配器封装现有部门服务与清理 facade，保留名称冲突、父级、所有引用、条件 SQL、删除版本、原启用状态和缓存失效规则。
- 交互回收站与自动清理复用同一份资源注册，历史部门归档保留独立清理适配器。

## API 合同

保留现有 POST `/admin/maintenance/recycle-bin/list`、`restore`、`purge` 路由，增加 POST `/resources`，请求为空对象，返回 `{ list: [{ resourceType, labelKey, canRestore, canPurge }] }`。目录只返回当前用户有回收站读取及业务读取权限的资源。

`resourceType` 从部门枚举改为受限逻辑字符串，并在服务端注册白名单校验。记录 ID 支持正整数或非空字符串，由适配器进一步验证具体业务 ID；部门继续使用正整数。列表保持现有摘要字段与分页结构，增加资源级 `canRestore` 能力，与已有 `canPurge` 一同返回；记录的可恢复性继续考虑保留期限。

通用服务检查回收站操作权限，并调用适配器的业务权限判定；提前清除始终要求当前登录身份 `isSuperAdmin`，可分配权限不能代替它。恢复和清除仍携带 `expectedDeletedTimeUtc`。期限与版本的最终校验须与业务条件 SQL 一致，不能以目录或前端能力代替服务端判断。

## 页面

资源目录驱动类型选择、默认选中首个可读资源和操作能力，不写死部门权限或类型。统一名称搜索、分页、删除人及时间展示、确认弹窗。无可读资源时显示空状态；目录或列表失败允许重试。

按资源分别分页，不新增跨资源合并排序。切换类型时清除旧选择、列表、搜索和页码；异步旧响应不能覆盖新资源，操作使用所选记录自身的资源键与删除版本。记录键包括资源类型，支持不同业务复用相同 ID。

页面文案使用本地中英文资源；资源名称由适配器给出的翻译键解析。资源级无恢复权限不应被展示为已过期。

## 验证与交付边界

改动前后分别检查后端和管理端 TypeScript。增加第二种仅测试用资源（含字符串 ID）验证目录、权限隔离、路由分发和清理自动接入；未注册资源、冲突注册及普通用户提前清除须失败。复用部门数据库测试检查恢复、过期、并发和引用规则无退化。

UI 使用隔离 mock 验证多资源、权限、切换时旧响应、字符串 ID、确认流程及原部门回归；运行 Node 和 Worker 相关调度测试、构建、变更文件格式检查和 `git diff --check`。本次不改变数据库结构，记录代码验证与线上验收为独立状态。
