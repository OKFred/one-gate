## 已实现行为

- `system_role` 使用公共软删除字段，普通记录和超级管理员种子显式写入 `false/null/null`；新增列没有数据库默认值。换表迁移保留 ID、原字段、权限绑定和自增高水位，建立活动名称部分唯一、清理索引与状态约束。
- 普通列表、详情、选择器、用户角色显示、授权与数据范围排除已删除角色。删除保留启用状态、部门范围和权限配置，不产生完整归档快照。
- 超级管理员角色 ID 1 在服务及最终删除/清理 SQL 中受到保护；任何用户引用都会阻止删除和永久清除，禁用用户也计入。
- 用户新增/修改的最终 SQL 验证全部目标角色处于未删除状态；保留现有禁用角色分配政策。角色权限关联的修改、计数和双方角色版本放在同一事务批次，换角色同时保护原归属和目标归属；零行修改不改变计数或版本。
- 15 秒撤销要求本人且当时仍有角色删除权限。30 天恢复使用回收站恢复权限与角色编辑权限；永久清除仍只允许当前超级管理员身份。
- 删除收据绑定精确删除版本；恢复检查原名称和全部保存的部门范围，保留原 ID/启用状态并重算权限数。时间边界使用数据库执行时钟，普通角色编辑保留原有单调版本行为。
- 部门软删除忽略回收站中的角色引用；部门永久清理检查全部角色。角色与部门都到期时允许部门记录积压，下一轮在角色清除后处理，不级联恢复或删除。
- 角色永久清理在同一 Node/D1 原子批次内移除所属权限绑定与角色，每条语句都重复状态、删除版本、期限和引用条件。恢复先成功时清理不删绑定；后续语句失败则整个批次回滚。
- HTTP 和冷启动分钟调度共用显式资源注册。每类每轮最多 100 条，记录清理数量、积压、最早超期时间、耗时和错误；失败不跳过其他资源，下一分钟重试。
- 角色页面通过通用 CRUD 的可选软删除配置复用既有撤销浮窗、登录会话隔离和资源变更通知。删除确认使用角色专属 30 天文案，按钮防重复提交。只有明确撤销成功才提示成功；未知结果和列表刷新失败分别处理。

新增接口为 `POST /api/v1/admin/system/role/deleteWithUndo`，请求含 `id`、可空 `expectedUpdateTimeUtc`，返回公共撤销收据。旧 `/role/delete` 继续返回数字；恢复、撤销和清除使用既有回收站接口。OpenAPI 已自动导出并生成前端类型，没有新增可分配撤销权限。

## 与计划的差异

| 项目                    | 实际处理与理由                                                                                             |
| ----------------------- | ---------------------------------------------------------------------------------------------------------- |
| 用户 service/prevention | 沿用现有前置校验，仅修改 repository 的最终 SQL，避免重复业务逻辑。                                         |
| 后端翻译                | 在角色领域导出错误翻译，由 `system/translation.ts` 汇总；不修改通用翻译初始化机制。                        |
| 角色权限批量写入        | 使用单个 JSON 参数代替原分片，避免 D1 参数上限和部分批次提交；计数/版本仅紧随成功关联变更更新。            |
| D1 预检                 | 增加只读 `role-soft-delete-preflight.sql` 和命令，输出七类异常计数；迁移自身仍用约束阻断异常，不能绕过。   |
| 定向 DDL                | 在仓库外由角色模型定向生成并核对；未运行会清空历史迁移的全量生成脚本。                                     |
| 既有测试                | 补齐显式删除字段；故意构造孤儿的授权测试改用原始夹具写入，以验证历史异常，而不绕过正常 repository 的保护。 |
| 本地联调                | 新增仅允许 loopback、外部配置启用的真实浏览器测试，正常完成 TOTP。测试身份、数据库、日志和截图在仓库外。   |

复查补齐了异常 JSON 的安全整数上界，以及通用 CRUD 同实例切换资源时的旧查询、删除确认和表单响应隔离。快速切换 A→B→A 也不会让旧保存响应关闭新表单；删除确认框关闭过渡保留本次文案，避免回落为通用硬删除提示。没有同时迁移用户、模板、任务或 Cron。

## 发布与恢复操作

1. 安排维护窗口，暂停角色编辑/删除、用户角色分配、角色权限绑定和相关部门范围写入。保存可恢复的数据库备份、当前应用版本及迁移账本；不要从已升级数据库直接运行旧硬删除代码。
2. 确认既有部门迁移及前序结构已完成。运行角色引用预检，七类计数必须全为零：用户角色数组/元素/孤儿、角色部门数组/元素/孤儿、角色权限孤儿。人工确认异常的正确关系后修复，不把错误 JSON 当空数组、不自动删除配置。
3. 旧 Node SQLite 在 `server/` 执行 `pnpm db:migrate:role:node --database=<现有本地 SQLite 文件的绝对路径>`。必须使用绝对路径：workspace 命令会进入 `apps/server/`，相对路径按该目录解析。脚本只处理固定 `0015`，事务成功后写校验和账本；已升级但无账本时拒绝，不重置删除状态。
4. D1 在 `server/` 执行 `pnpm db:preflight:role:worker:remote`（只读），确认零计数后执行既有 `pnpm db:migrate:worker:remote`，随后 `pnpm db:check:worker:remote`。本地演练使用对应 `:local` 命令；本次未运行任何 `:remote` 命令。本轮验证了新库角色 DDL/正常种子，不能据此宣称现有全量初始化覆盖全部历史结构：新空库需另行核对完整结构与迁移账本基线，不对已升级角色表重复套用 `0015`。
5. 验证字段/默认值/状态约束、ID/数据/绑定/高水位、活动唯一、普通查询隐藏、引用阻断、本人删除权限撤销、回收站双权限和超级管理员清除。确认 Node/Worker 分钟调度能观察到 `role` 清理事件后再恢复写入。
6. 本次 `0015` 事务失败会回滚；Wrangler 整目录 apply 按单个迁移提交，后续失败不会回滚已经成功的前序迁移。保留停写状态，核对账本并依据异常摘要修复后重试。若新版发布后需要回退，必须使用备份及对应应用版本制定恢复方案，不能删除成功标记或直接重复换表。备份恢复后按独立保存的删除请求记录重新落实删除，再开放访问。

操作人员应关注 `soft_delete_cleanup`、`soft_delete_cleanup_failed` 的 `module=role`，以及 `remainingExpired`、`oldestExpiredTimeUtc`、`overdueMs`。持续积压可能来自用户引用、角色/部门处理顺序或数据库失败，需要处理原因；日志本身不等于已接入外部告警。

30 天仍是误删恢复窗口，适用删除请求可以由超级管理员提前清除。本期没有扩大历史归档清理来源，也没有宣称完成全站隐私合规；备份、其他业务数据、日志和第三方副本分别治理。
