# 定时任务诊断与初始化优化详细设计

日期：2026-10-23。基线：`main@9c5942cf`。开发分支：`codex/hodor-maintenance-diagnostics`。

## 目标和证据边界

修复已确认的诊断信息丢失，再移除 Worker 定时入口不必要的 HTTP 路由构造。保留 D1、SQLite、PostgreSQL 的现有任务范围、并发等待、保留期和权限行为。

已确认两个诊断缺口：手机客户端只保留 HTTP 状态，维护调度器在所有任务完成后仅抛出统一错误。客户端由 `one-autojs6` 对话继续负责，已提交 `981af89` 的脱敏摘要，本轮继续核验其是否能在白名单范围内区分安全原因。

Presence 422 已由客户端对话定位为设备身份配置误用测试值，修正为原有身份后得到 `200 + ok:true`。本轮用自然流量和 D1 聚合只读复核。Device Info 422 单独跟踪。历史 D1 83 个失败 span 涉及 19 个 trace，均为旧版本的连接断开；这些数字不是独立事故数量。CPU 超限与 D1 断连之间尚无直接因果证据。

## 安全的失败诊断

- 定时任务使用代码内固定名称与执行函数组成描述对象，不使用管理员可编辑的任务名、URL、SQL 或参数作为日志标签。
- 每次调度生成一个关联 ID，记录每个失败任务的固定名称、安全原因码和耗时；汇总记录总任务数与失败数。继续等待其他任务完成后再让调度失败，避免一项异常跳过回收站清理。
- 原始异常可能携带 SQL、参数、连接串和凭据，不直接序列化 message、stack、cause 或异常对象。原因分类只输出固定枚举，并对有限深度的 cause 链进行白名单识别；未知错误保留为 unknown。
- 回收站资源适配器已自行捕获错误，需在该层保留相同安全原因，避免调度层只能看到统一清理失败。既有清理错误码兼容保留。
- 不新增即时重试；失败留给下一个现有分钟 tick。代码中的所有 Promise 继续由 await 或 waitUntil 跟踪。
- Node、D1 Worker 和 PostgreSQL Worker 使用相同诊断包装；PostgreSQL 仍只运行已有保留期任务。

## 初始化拆分

现状：scheduled 调用 getApp，构造完整 HTTP / OpenAPI 应用以间接初始化跨域服务注册表。当前本地应用构造 374 条路由。

方案：保留完整的管理员服务注册表，提供幂等的 ensure 初始化入口。HTTP 入口和 scheduled 入口共用该入口；scheduled 不调用 createApp。绑定及环境注入先于注册和任务执行；首次事件即 scheduled 也必须可调用 registry。重复 tick 和后续 fetch 不重复初始化注册表。

本轮优化范围是路由与 schema 的运行时构造。静态模块依赖、业务 Cron 执行器的全量扫描和响应体大小边界另行评估，不能把本轮结果描述为已消除全部冷启动或 CPU 超限。

## 验证

基线记录 TypeScript 诊断和现有定时测试。覆盖单项/多项失败、同步抛出、未知异常、嵌套 cause 与敏感内容、其他任务完成后汇总失败、下一个 tick 可再执行，以及清理资源错误原因保留。

初始化覆盖 scheduled 先于 fetch、fetch 先于 scheduled、重复 tick、D1 与 PostgreSQL 路径、HTTP 端点和回收站回归。以真实 workerd 本地集成验证和本地 CPU 对比区分功能与性能证据；生产 CPU 收益必须在发布后的实际调用中验证，不能以 Node 耗时代替线上测量。

生产核查仅观察自然流量、查询聚合和现有历史证据。本轮不改变远端配置、数据库、设备凭据或部署版本。无需数据库迁移。
