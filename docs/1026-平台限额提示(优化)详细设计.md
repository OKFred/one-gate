# 平台限额提示详细设计

## 问题与目标

登录依赖 D1、KV 等平台服务，当前限额错误会进入通用异常分支，数据库翻译不可用时甚至直接返回 `errorHandler.unknownError`。本次增加公共限额分类及前端兜底，让未登录用户也能看到可行动的原因，不需要先成功读取数据库或翻译数据。

## 后端

- 在全局错误处理中、SQL 通用归类之前识别明确的 Cloudflare 错误。只检查有界 cause 链的数据属性，不展开 SQL、参数、Key、任意 getters 或循环引用。
- D1 每日读取、写入和容量分别分类；KV 明确的每日额度与短期限流分开；Workers 每日请求额度与 CPU/内存资源超限分开。不把普通 429、SQL 错误、网络故障或业务文案统一归为额度耗尽。
- 保持 `{ok:false,message,data:{code,details:[]}}` 结构，额度/容量/运行资源故障返回 503，短期限流返回 429；保留 request ID 与结构化日志。新增固定业务码，不透传供应商原文。
- 已识别的平台故障使用随代码发布的中英文安全文案，不调用可能已经失败的 D1/KV 翻译依赖。公共种子仍登记对应后端词条，但运行时提示不依赖同步种子。

## 前端

- 共享请求层支持稳定业务码及明确的 Cloudflare 边缘错误页；Workers 请求若在应用执行前被平台拒绝，仍可在响应可读时给出说明。
- 同时覆盖 HTTP 错误与 HTTP 200 + `ok:false`。认证、TOTP、身份切换、局部错误展示及不自动重试写请求的既有行为保持。
- CORS 或断网导致没有可读状态/正文时，只提示服务暂不可达及管理员检查平台状态，不断言某项额度已耗尽。普通 429 不归类为套餐额度；边缘 1102 不武断区分 CPU 与内存。
- 文案随共享 UI 发布，中英文齐备；同一次失败只展示一次，不新增页面内重复 snackbar。

## 数据与发布边界

无模型、迁移、权限、菜单及种子执行变更，不调整套餐、不清理数据、不扩大凭据权限。先在最新 main 创建开发分支验证，代码交付与生产发布分开记录。

## 验证

覆盖 Drizzle 包装的 D1 日读/写限额、KV 日额度与热键 429、Workers 1027/1102、普通错误负例、循环 cause、敏感内容不外泄，以及翻译依赖不可用仍返回明确提示。前端验证登录页、英文、HTTP 200 业务失败、边缘页、无响应、局部提示及认证回归；执行前后 TypeScript 比对、定向测试、构建、格式检查与 git diff --check。
