# 角色软删除详细设计

## 迭代目标与基线

2026-10-11，用户选择下一轮扩展软删除到其他业务。基于 `one-gate/main` 的 `1fba2f9f` 规划，建议本轮仅接入系统角色，实施分支为 `codex/role-soft-delete`，创建时重新同步最新 main。

交付角色的 30 天回收站、15 秒撤销、到期清理，以及通用 CRUD 的可选软删除接入能力。复用现有资源注册表、回收站页面、撤销协调器和分钟调度，不建设第二套回收站。

## 资源选择

| 资源             | 现有依赖与恢复价值                                                     | 顺序                                          |
| ---------------- | ---------------------------------------------------------------------- | --------------------------------------------- |
| 系统角色         | 用户角色数组、角色权限绑定、部门范围；误删恢复可保留原授权配置         | 本轮，仅新增这一类资源                        |
| 普通邮件模板     | 模板正文和名称，发信按 ID/名称读取；安全通知还依赖系统保留模板         | 后续候选，先明确保留模板及管理范围            |
| 系统用户         | 登录、JWT、OAuth/SSO、个人配置、邮件等关联数据                         | 单独迭代，先定义身份与个人数据的恢复/清除政策 |
| API Task 与 Cron | 任务 key、调度、执行日志与财务数据源；key 复用可能改变既有 Cron 的关联 | 作为配套迭代，明确在途执行与恢复调度规则      |

当前角色直接硬删除，只有超级管理员角色保护。普通查询和授权查询未定义软删除状态；用户分配角色、角色权限写入主要采用前置存在性校验。公共回收站及撤销工具已经具备多资源合同，而 `SchemaCrudPage` 的删除合同仍为普通 `{id}` 请求。这些是静态代码确认的接入缺口，不是本轮已复现的线上故障。

## 数据模型与查询

`system_role` 增加 `softDeleteColumns()`：`is_deleted` 为 Drizzle boolean/SQLite INTEGER，`deleted_time_utc` 和 `deleter_id` 可空。使用现有状态一致性约束，新增记录和超级管理员种子显式初始化 `false/null/null`，普通新增/编辑请求不能提交这些字段。保留期及撤销截止时间继续由删除时间计算，不新增到期时间列，不新增数据库默认值。

名称改为 `is_deleted=0` 生效的部分唯一索引；添加删除时间清理索引。删除保留 ID、名称、备注、启用状态、部门范围及创建/更新审计字段。普通列表、详情、名称查询、选择器、编辑、用户角色展示、授权角色和权限查询排除已删除角色。

所有新增角色属性需从普通 VO、排序和写入类型中明确分离；不能因 ORM 的完整行类型扩展而意外暴露系统字段。角色列表供删除操作使用的 `updateTimeUtc` 必须可空且与页面记录一致。

## 删除、引用与授权

1. 超级管理员角色 ID 1 始终禁止软删除和永久清理。业务层及最终条件 SQL 均保护该 ID。
2. 任一用户的 `role_id_arr` 引用目标角色时拒绝删除，包含禁用用户；不自动解绑用户。用户表本轮不增加软删除字段。
3. 用户新增、编辑及其他角色分配入口使用最终写 SQL 验证所有目标角色未删除。启用状态沿用原分配规则，不把禁用角色等同于已删除角色。
4. 删除使用单条条件 UPDATE，包含活动状态、无用户引用和超级管理员保护；新 `deleteWithUndo` 接口额外比对页面预期更新版本并返回实际删除时间。原 `{id}` 接口保留无页面版本的兼容合同。重复删除不续期。新删除时间未晚于上一更新版本时返回冲突。
5. 角色权限绑定作为角色拥有的配置保留在 `system_role_permission`，不单独进入回收站。角色删除后，其绑定不参与授权，也不能通过普通绑定管理接口读取或改动。
6. 权限绑定的单条及批量新增、修改、删除和权限计数更新都需验证所属角色活动状态。编辑关联允许变更 `roleId`，实际写 SQL 同时检查记录当前所属角色与目标角色未删除；同一原子操作重算旧、新两个角色的计数并推进各自更新时间。只改 `permissionId` 时仍检查当前所属角色。记录已移走或更新零行时，关联、两方计数和版本均不改变并返回冲突，避免从回收站角色搬走绑定或使旧页面删除版本继续有效。
7. 授权查询、数据范围查询和超级管理员权限捷径统一采用未删除角色过滤；保留现有权限/菜单有效性规则。删除、撤销、恢复及清理调用现有缓存失效机制。

用户角色 JSON 和角色部门范围 JSON 在迁移预检中检查格式、ID 类型及孤儿引用。异常数据输出摘要并阻止开放新版写入；不能把解析失败视为无引用，也不自动删除或改写历史配置。

## 与部门软删除的协作

| 操作           | 角色部门范围的处理                                       |
| -------------- | -------------------------------------------------------- |
| 部门软删除     | 仅未删除角色的部门范围阻断删除，禁用但未删除角色仍阻断   |
| 部门永久清理   | 所有角色记录均参与引用检查，包含回收站中的角色           |
| 角色撤销或恢复 | SQL 验证保存的部门 ID 全部存在且未删除；不可用则明确拒绝 |

保留现有部门范围引用含义；不借本次接入重新解释 `dataScope` 或默默清空 `customDeptIds`。恢复冲突时先恢复相关部门，或先处理冲突角色，不自动恢复部门或调整范围。

如果角色与部门同时到期，部门被角色引用阻断时记录积压；角色清理完成后由下一分钟再处理部门。资源之间不自动级联删除。

## 恢复和权限绑定

恢复保留原 ID、启用状态、部门范围和当前仍保留的权限绑定；清空三个删除字段。不重新分配用户、不重建已经失效或移除的权限、不绕过当前权限/菜单有效性判断。`permissionCount` 按当前关联数量重算，不能直接依赖删除前的缓存计数。

30 天恢复通过现有回收站恢复权限及角色编辑权限；15 秒撤销要求本次删除人及当前角色删除权限，不要求回收站恢复权限。恢复和撤销都以 SQL 执行时检查状态、精确删除版本、期限、部门有效性，名称冲突由活跃唯一索引保证。满 15 秒/30 天均失去对应资格，重试不延长期限。

角色恢复与权限计数更新使用同一原子操作。批处理中的每条关键语句都带状态和版本条件；零行更新不是数据库错误，必须根据最终返回结果判断成功，不能因事务未抛异常就宣称已恢复。

## 永久清理

提前清除要求当前身份为真正超级管理员，并携带预期删除版本；到期清理由显式注册的角色适配器接入现有分钟入口，每轮最多清理 100 个角色。

清理必须同时删除角色及其内部权限绑定。Node 使用已有驱动支持的原子事务/批处理；D1 使用事务性 `batch()`。绑定删除和角色删除均检查同一角色状态、删除版本、期限或提前清除资格、无用户引用及 ID 1 保护，确保恢复竞争时不会先丢失权限绑定。数据库执行错误须整体回滚；不把关联清除放在独立的后续请求。

D1 官方说明批处理按顺序执行，语句失败时中止或回滚整个序列；具体实现仍需真实 Node/本地 D1 验证，不能仅依靠统一驱动类型断言。[D1 batch 文档](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)

复用 `deletedCount/remainingExpired/oldestExpiredTimeUtc/durationMs` 及失败、积压事件，按 `role` 区分资源。角色适配器失败不能跳过部门清理。当前角色删除路径没有完整审计快照调用，本轮不新增快照，也不扩大现有历史部门归档的清理范围。

## API 与前端

| 接口，均为 POST 且位于 `/api/v1`           | 合同                                                           |
| ------------------------------------------ | -------------------------------------------------------------- |
| `/admin/system/role/delete`                | 保留 `{id}` 和原数值响应，改为受引用保护的软删除               |
| `/admin/system/role/deleteWithUndo`        | `{id, expectedUpdateTimeUtc}`，版本允许 null；返回公共撤销收据 |
| `/admin/maintenance/recycle-bin/resources` | 动态目录增加可读的 `role`，使用已有角色名称翻译键              |
| 现有回收站 list/restore/purge/undo         | 通过 `resourceType: role` 分发，不新增角色专属回收站路由       |

新增角色专属重名、引用、部门范围不可用、版本冲突等稳定业务码及中英文文案；同步 OpenAPI 和 API 封装。不新增可分配撤销权限。

`SchemaCrudConfig` 增加可选 `softDelete` 配置：资源类型、记录显示名、页面更新版本、删除调用、已有详情/列表确认、回收站访问能力、业务错误分类及确认文案。角色确认文案说明进入回收站、保留 30 天；未配置资源继续使用原提示，不修改共享默认删除词条。`SchemaCrudPage` 调用既有 `showDeleteUndo`，并订阅资源变更。未配置资源沿用原删除行为，部门树无需迁入 CRUD。

查询刷新需能返回成功状态并只接纳最新查询。删除、撤销结果与列表刷新结果分别处理：明确成功才提示已撤销；响应丢失或无法确认时显示结果未知；恢复成功但刷新失败仍保留成功结论并提供刷新。浮窗沿用原身份隔离、期限、手动重试及只展示一次错误规则。

错误分类同时识别 HTTP 错误与 `HTTP 200 + ok:false`，按稳定业务码处理。重名及部门范围冲突可在原期限内手动重试；旧版本、权限不足或过期关闭入口；超时、断网及无法确认提交结果的 5xx 保持未知。现有详情/列表查不到记录不能证明已永久清除；查到活动记录只能确认当前状态，不能证明本次撤销请求执行成功。没有可信删除收据时不生成撤销入口，不自动重发删除，也不新增专用状态查询接口。

## 迁移与发布

现有 D1 迁移末尾为 0014，暂定新增 `0015_role_soft_delete.sql`，实施时核对编号冲突。受控换表保留全部原字段、ID、原数据及自增序列高水位；回填 `0/null/null`，保留权限关联。不直接运行会删除历史迁移目录的全量 DDL 生成脚本；定向生成并核对本次 DDL。

Node 增加固定本次迁移的事务脚本，包含校验和账本、重复执行保护、完整性检查和失败回滚。同步新库建表 SQL、超级管理员种子和 D1 结构契约；新空库初始化与旧库升级分别验收。D1 追加迁移，不改历史文件。[D1 migrations 文档](https://developers.cloudflare.com/d1/reference/migrations/)

发布需暂停角色、用户角色分配、角色权限和相关部门范围写入，避免旧代码与新结构混跑。备份、迁移、结构检查及新版验收完成后恢复访问。当前公开 CI 只做验证，发布走独立私有流程；不能沿用旧 dev 自动部署文档中的合并即发布假设。旧代码不识别新字段，迁移后不能仅回退应用就开放访问。

30 天沿用现有误删恢复窗口。备份恢复及其他业务数据治理沿用已明确的独立边界，本轮不扩展成全站删除请求系统。

## 实施顺序

1. 数据与安全：角色迁移、初始化、活跃查询、用户引用及权限绑定原子写入。
2. 生命周期：角色删除/恢复/清理/撤销、部门引用协作、资源注册及缓存失效。
3. 页面与交付：CRUD 可选配置、角色 UI/API/翻译、双运行时及 UI 验收、维护窗口说明与实际落地记录。

三个阶段构成一个完整迭代；不得仅给角色增加字段或只改删除按钮后就宣告接入完成。
