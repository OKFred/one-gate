# 私人日历实际落地

## 实现结果

独立 `/calendar` 页面提供月历、所选日期日程、接下来 5 条、新增、编辑和取消。首页仅增加日历入口。跨日事件按北京时间的半开日期窗口显示，编辑未改动的时间保留原秒和毫秒。

提醒仅在站内展示。已登录且通过安全验证的管理端页面可见时检查；隐藏时暂停，重新打开时补待处理提醒。只有明确确认成功才移除提醒。未创建 Codex 自动化、后台定时任务、邮件或系统通知。

7 个 POST 接口、SQLite/D1 与 PostgreSQL 仓储及 OpenAPI 类型已实现。owner 只取人类 principal，API Token 不可访问，超级管理员也不能越权查看其他账号的日程。创建按本人 requestKey 幂等；修改、取消和提醒确认均检查原版本，SQL 保留并发确认结果。

## 与计划的差异

- `update_time_utc` 明确为非空，创建时与创建时间一起由服务赋值，未增加数据库默认值。
- 创建重放返回当前实体；如果另一标签已经编辑会明确请求冲突，已经取消则提示状态变化，不误报保存、不复活、不重复创建。
- 回归暴露地图重试时 MUI 写入 className 覆盖 Leaflet 自有类的竞态。改为外层主题样式、内层原生地图容器，保持原断言与键盘操作。
- 首页异步回归增加等待新列表完成的同步点，避免旧列表的多个元素触发严格选择器错误。未降低产品断言。
- CI 仅追加日历 DDL、Worker 与页面测试选择范围；沿用既有本地验证和用户授权的 Actions 跳过方式，没有修改分支保护。

## 上线与首条真实日程

D1 仅应用新增 `0020_personal_calendar.sql`，Node 提供显式本地文件事务脚本，PG 仅追加 `0003_personal_calendar.sql`。不运行 db:init、reset、全量重建或历史回灌。

生产版本、发布前备份、增量迁移、资源绑定核对及首条真实日程的创建/重读证据独立保存在仓库外。用户的具体标题、日期和链接不写入公共迁移、测试、种子或本文件。代码验证、隔离演练与真实上线验收分别记录，不能相互替代。

## 边界与后续

没有新增未解决的应用 TypeScript 诊断。当前仅一次性私人日程、北京时间 UI 和站内提醒；关闭站点期间不会后台推送。重复日程、其他时区的编辑体验、完成状态及站外通知可作为后续独立需求。
