# 私人日历 ICS 订阅实际落地

## 本轮状态

实现位于 `codex/calendar-subscription-health`，基于 main `15388c9d`。本记录固化代码、定向迁移和本地验证结果，后续提交、部署版本与生产迁移以独立发布回执为准。没有创建真实订阅凭据；真实 Apple 设备订阅与刷新尚未验收。

## 实际实现与计划差异

- 日历增加“订阅”入口。默认关闭说明折叠区，生成/重置与停用均需明确确认；链接仅当次返回并在内存中显示，可显式复制 HTTPS 地址。
- 三个管理 POST 接口沿用登录与 TOTP，仅 human principal 可管理本人订阅；客户端不能注入 owner、摘要、明文 token 或版本。CAS 版本冲突、未知提交结果和身份变化均单独处理，不自动重试写操作。
- GET/HEAD `/calendar-subscription.ics` 是独立外部协议资源，位于业务 `/api/v1` 之外。未改既有鉴权旁路或 TOTP 路径分类，未新增可分配权限。仅准确路径、规范单个 token 查询和允许方法可访问。
- 数据库只存 256-bit 随机 token 的 SHA-256 摘要。重置与停用使旧链接立即失效；完整 feed 查询同时再次检查摘要、版本和有效 owner。站内提醒确认不删除 ICS 的 VALARM。
- 遵守 RFC5545 的转义、CRLF、UTF-8 75-octet 折行、稳定 UID 与 SEQUENCE，使用 UTC 时间；无结束时间不捏造时长。所有活动事件完整输出，1000 条或 2 MiB 上限超出时整体失败，不返回截断快照。非法数据同样整体失败。
- 管理和协议成功/失败响应均明确禁止私有及 CDN 缓存。协议不提供 ETag/304。配置固定 HTTPS origin，忽略请求 Host/Forwarded，不在应用日志输出链接、token、ICS 或完整日程。
- 额外修复 Node 注册顺序：订阅协议先于静态文件中间件，避免部署目录中的同名文件绕过协议校验。普通静态资源与 healthCheck 保持可用。
- 相比计划，首期只提供 HTTPS 复制和 Apple 接入说明，暂不唤起 `webcal:`，避免给传输安全和客户端差异作额外承诺。关闭窗口、离页或身份切换即清除链接；已有链接无法通过状态查询重新显示。
- UI 将响应丢失保留为“结果无法确认”，先手动刷新状态再允许新写入；状态变化清除旧链接。剪贴板成功/失败回调也绑定代际，不能覆盖之后的重置、停用或刷新结果；刷新中禁止复制可能过期的链接。

## 迁移与旧数据

新增表 `personal_calendar_subscription`，5 列、可空唯一摘要，无数据库默认值。SQLite/D1 与 PostgreSQL 同构；服务显式初始化字段，不种入任何订阅。

- D1 新增 `0021_personal_calendar_subscription.sql`，附独立结构契约并追加现有总契约。
- PostgreSQL 新增 `0004_personal_calendar_subscription.sql`，仅精确开放本次三个管理路由；原健康模块仍未开放 PG 能力。
- Node 提供 `pnpm run db:migrate:calendar-subscription:node`，建表、契约核对与 checksum 成功标记同事务，重复执行保护，失败整体回滚。
- 使用定向 `db:generate:calendar-subscription`；未执行全量初始化、reset 或生产 seed。50 份历史迁移 Git blob 和 SHA-256 前后相同。

## 上线操作与验收边界

1. 发布前备份并检查现有迁移 ledger，先应用本次新增迁移；不重新初始化既有库，也不补全量种子。三种部署只执行自己后端的流程，Node 升级暂停相关写入。
2. 设置 `CALENDAR_SUBSCRIPTION_ORIGIN` 为固定 HTTPS API origin，不能带路径、查询、用户名或密码。留空时界面明确不可生成，feed 返回不可用；已有订阅仍可在管理接口停用。模板见 `server/apps/server/.env.example`。
3. 外部 Apple 客户端不能完成站点交互式登录。若有 Cloudflare Access，需单独核对精确 `/calendar-subscription.ics` 的路径规则，只交给本协议 token 验证；其余 host、管理 API、登录及 TOTP 保留原保护。当前尚未修改此规则或启用真实凭据。
4. 应用仅记录路由模板。Cloudflare 平台访问/Trace/tail 可能包含完整 request URL，须核对相关日志排除或脱敏及访问权限，不能宣称 query secret 天然不会被平台保存；不要在普通日志采集或公开报告粘贴订阅地址。
5. 配置与规则就绪后，由用户本人生成链接并在 Apple Calendar 添加订阅，核对正确日程、时间与提醒；另验重置/停用的旧链接失效、取消事件同步、账号停用、未登录管理接口拒绝。iCloud/客户端可能保存已经下载的副本，停用服务端链接不等于移除这些副本。

后续可在真实设备确认客户端刷新与提醒行为，再考虑受控条件缓存；本轮不增加 CalDAV、双向编辑、外部推送或后台定时任务。
