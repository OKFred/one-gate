# AI 协作与复盘工作流指南 (AI Collaboration & Review Workflow)

本指南面向所有涉及代码修改与 AI 交互的场景，规定从需求分析到代码编写、自动修复、多次复盘校验以及交付落地报告的全流程工作流。

---

## 1. 大型改动需求分析与设计计划文档 (Large Change Design & Plan Docs)

在需求分析阶段，若遇到改动比较大的需求（例如涉及多模块重构、架构变动或较多代码修改）：
必须在代码编写前先输出两份设计与计划文档（文档命名格式为 `MMDD-xx(功能|优化)详细设计.md` 与 `MMDD-xx(功能|优化)计划变更.md`，例如 `0725-路由加载器(优化)详细设计.md`）：
1. `MMDD-xx(功能|优化)详细设计.md`：详细阐述需求背景、技术方案及架构设计。
2. `MMDD-xx(功能|优化)计划变更.md`：记录预计变更的文件列表、接口变动及预期影响范围。

---

## 2. 代码修改后的 ESLint / Prettier 自动修复 (Pre-Loop ESLint/Prettier Fix)

在每次完成文件或代码修改后、**进入多次复盘校验循环之前**：
- 必须对本次修改涉及的文件执行简单的 ESLint / Prettier 代码规范修复（例如针对修改过的文件运行 `npx eslint --fix <files>` / `npx prettier --write <files>` 或调用所在包的 `pnpm run lint` / `pnpm run format`）。
- 确保所有修改过的代码在进入规范对比校验前，已自动消灭缩进格式、末尾逗号、未使用的 import 等基础代码风格缺陷。

---

## 3. 代码修改多次复盘机制 (Review & Stage Loop)

每次 AI 对话中若涉及文件或代码修改，在完成 ESLint / Prettier 格式化修复后，必须参照 `AGENTS.md` 及其引用的各项开发规范文档（`global.md`、`workflow.md`、`backend.md`、`frontend.md` 等），对本次新增/变更的代码进行多次复盘校验。

- 若复盘发现新增改动与规范要求存在出入：
  1. **暂存当前改动**：先将当前已完成格式化与修正的改动进行 stage 暂存（如执行 `git add`）。
  2. **重新修正代码**：依据规范针对出入点重新修改代码。
  3. **代码格式修复**：再次对修正后的文件进行 ESLint / Prettier 修复。
  4. **再次对比校验**：重新检查最新修改的内容是否与规范有出入。
  5. **循环上限**：以上“校验 -> stage -> 修正 -> 校验”流程最多反复 **5 次**；若已完全满足规范，则立刻终止循环。

---

## 4. 复盘完成后的交付与落地比对文档 (Post-Review Handover & Actual Implementation Doc)

在循环检查完成、确定不再改动代码之后：
1. **告知开发者复盘次数**：在对话中明确告知开发者本次对话一共重新复盘（循环校验）了几次。
2. **输出实际落地对比文档**：输出 `MMDD-xx(功能|优化)实际落地.md`，比对【实际改动】与【计划变更】的差异之处：
   - 如果一致，自然最好；
   - 如果不一致，必须突出说明哪些地方 **不改** / **多改** / **少改** 了，并说明具体理由。
3. **后续建议收尾**：在落地文档结尾，必须给到开发者后续优化或者功能开发的建议。

---

## 5. 规范修改限制原则 (Specification Editing Restrictions)

除非属于以下两种例外情况，否则在任何时候都不允许去修改规范文件（包括但不限于 `.agents/` 目录下的所有规范）：
1. 开发者显式说明/指示需要修改规范；
2. 开发者的要求与现有规范存在出入，需要调整规范。
除上述两种情况外，严禁任何擅自修改、篡改或削弱规范的行为。
